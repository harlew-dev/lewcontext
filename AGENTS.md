# Project guide: lewcontext

## Product and stack

This project replaces the previous project completely. The previous README was stale and was not used as project context. The current README documents the new application.

- Backend: Go 1.26+, standard-library `net/http` method-aware routing, Bun (`uptrace/bun`, pgdialect) over the pgx `database/sql` driver, PostgreSQL 15+. In production the same Go binary serves the web app (`internal/web`, the build embedded with `//go:embed`): one process, one origin.
- Frontend: React 18, TypeScript in strict mode, a single-page app on React Router v7 framework mode (`ssr: false`; public pages such as `/` prerendered at build time for SEO), built by Vite, Tailwind CSS v4 on top of Uber Base Web (`baseui`) behaviour, SWR, Heroicons, `motion` (sliding sidebar indicator and the hover/focus highlight in the sidebar, tabs, menus and listboxes), Inter (self-hosted via Fontsource).
- Component standard: `components/ui` holds the app's Tailwind components (restrained zinc styling, sidebar and auth layouts). Match the existing components' APIs, class patterns and data attributes when adding or changing one.
- Testing: Go testing + httptest + race detector + real PostgreSQL integration tests; Vitest + React Testing Library; Playwright end-to-end tests. ESLint, TypeScript, go vet, gofmt, Prettier.
- This is a working demo of authenticated Go API ↔ React communication with durable PostgreSQL projects, not a static mockup.

## Docs and plans

Short summaries of how each part works live in `docs/`, indexed in [`docs/README.md`](docs/README.md). They hold the project's standards: naming, patterns, security rules and known pitfalls that the code alone doesn't show.

**Always read the docs for an area before writing code that affects it.** This isn't optional, even for small changes, and it applies to subagents too:

1. Before the first edit, find every area the change touches in the table below, and read each of those docs in full. Most changes touch more than one: a new endpoint touches `endpoints.md`, `auth.md`, `rate-limits.md`, `database.md` and `api/testing.md`, plus `ui/api.md` if the web app calls it. A new component touches `ui/design.md` and `ui/base-ui.md`.
2. If the work has a plan in `plans/features/` (open) or `plans/features/implemented/` (shipped), read it too. Its confirmed decisions override your defaults.
3. Follow what the docs say over what you'd otherwise do. If a doc and the code disagree, or a doc's rule doesn't fit the task, stop and tell the user; don't silently pick one.
4. Update every doc whose summary the change makes untrue, in the same change. A new doc gets a row in `docs/README.md` and in the table below.
5. **Don't work around a failing convention check** (`docs/checks.md`): rename your code to follow `docs/naming.md`, never loosen, skip or add an exception to a check without the user's agreement, and ask the user when `naming.md` doesn't settle a name.

## Non-negotiable architecture conventions

1. Keep source files focused and readable. Split business rules, persistence, HTTP boundaries, and presentation into named functions and small modules. Avoid large single-file apps and dense one-line functions.
2. Components are only for UI that is reused. Reuse shared buttons, form controls, headings, descriptions, badges, notices, layout, loading, empty states, and dialogs. Extend an existing primitive before duplicating markup/styles. Use BaseUI for interactive controls and accessible overlays; do not build a second component library beside it.
3. Content unique to one page lives in that page file (`src/pages/...`), split into named local functions; do not create `components/` files such as `DashboardPage` or a section used by a single page. `src/components` holds only reused UI: generic primitives in `components/ui`, page chrome in `components/layout`, and feature UI shared by several app pages in `components/app/<feature>` (e.g. `components/app/projects`). When page-local UI becomes needed by a second page, move it into `components/`. Use typed props and shared domain types.
4. Pages are nested by area: `src/pages/home.tsx` (the public, prerendered `/`), `src/pages/auth/*` (signed-out, e.g. `/auth/login`) `src/pages/app/*` (signed-in; workspace pages under `src/pages/app/[workspace]/*`, e.g. `/app/wsp_…/dashboard`, `/app/wsp_…/projects`, plus `/app/onboarding`, `/app/verify-email` and the account's `/app/settings`) and `src/pages/admin/*` (the admin dashboard at `/admin/<ADMIN_ROUTE_KEY>`, inside `pages/admin/layout.tsx` and `AdminLayout`; `docs/api/admin.md`). Every page is registered with its URL in `apps/web/src/routes.ts`. Signed-in pages render only their content inside the `pages/app/layout.tsx` layout route, which wraps them in `ApplicationLayout` and stays mounted between pages (sidebar state, the sliding `layoutId` indicator). Page route constants live in `apps/web/src/lib/routes.ts`; API paths and calls live only in the typed client `apps/web/src/lib/api/<resource>.ts` (`const api = useApi()` then `api.projects(workspace.id).store()`; typed paths via `paths.projects(workspace.id).index()`). Names follow [`docs/naming.md`](docs/naming.md): API client methods use the API's actions (`index`, `show`, `store`, `update`, `destroy`), page route constants are grouped by resource with page actions (`routes.projects.show(ws, prj)`, `routes.workspaces.edit(ws)`), and resource pages export `<Resource><Action>` (`ProjectIndex`); components read the session with `useSession()` (`apps/web/src/lib/session.tsx`) and the current workspace with `useWorkspace()` (`apps/web/src/lib/workspace.tsx`); shared route loaders live in `apps/web/src/lib/loaders.ts`; the API and page registry is `apps/api/internal/httpapi/router/routes.go`. Do not put route declarations in `main.go` or `root.tsx`.
5. Go `cmd` contains composition, process startup/shutdown, migration, seed and prune entrypoints, and the operator's commands (`cmd/admin`: granting and revoking admin, resetting MFA, suspending and unsuspending, signing everyone out, listing and unblocking blocked email addresses, generating keys), only. `internal/httpapi` owns transport/input validation: its core (the `Server`, middleware, JSON answers, rate limits, sessions) at the top, controllers in `internal/httpapi/endpoints/<area>` (`account`, `workspace`, `admin`; one controller per file, e.g. `workspace.Projects`; areas never import each other), the registry in `internal/httpapi/router`, and only tests import `internal/httpapi/apitest` (`TestHTTPLayout`, [`docs/naming.md`](docs/naming.md#controllers-internalhttpapi)); `internal/store` owns Bun models and queries; `internal/auth` owns auth primitives; `internal/config` owns environment validation; `internal/database` owns connection and migration setup, the advisory locks (the email lock, the IP blocks cap's, the metrics rollup's) and the slow-query hook; `internal/web` owns serving the embedded web builds (the app's prerendered pages, SPA fallback and assets; the admin build's shell and its `/admin-assets/` files, served only with the assets pass; page security headers and CSP); `internal/observe` owns the log handler every command installs, request IDs, what each request's access line reports, the scrubber for error text, the error collector behind `app_errors`, and the metric registry with its minute's flush and `/metrics` (it imports nothing else of the app's).
6. Build UI with Tailwind utilities in markup, Tailwind's default palette (zinc), spacing and mobile-first breakpoints (`sm:`, `lg:`), and `dark:` variants for the system colour scheme. Do not add per-component CSS files or custom colour tokens; `src/styles/theme.css` only sets the font, `src/styles/base.css` holds element defaults, both imported by `src/styles/globals.css`.
   - Component files are kebab-case and group a family of named exports: `button.tsx`, `input.tsx` (`Input`, `InputGroup`), `fieldset.tsx` (`Fieldset`, `Legend`, `FieldGroup`, `Field`, `Label`, `Description`, `ErrorMessage`), `dialog.tsx`, `confirmation-dialog.tsx` (`ConfirmationDialog`, for every "are you sure?"), `dropdown.tsx`, `listbox.tsx`, `sidebar.tsx`, `navbar.tsx`, `table.tsx`, `text.tsx`, `heading.tsx`. Layouts are `components/layout/sidebar-layout.tsx`, `auth-layout.tsx` and `application-layout.tsx`.
   - Components in `components/ui` keep their established props (`<Button color|outline|plain href>`, `<Badge color>`, `<Dialog open onClose size>`, `<SidebarItem href current>`). Other components with alternatives use a `variant` prop (`<Notice variant="error">`); never `tone` or one component per alternative.
   - BaseUI stays underneath for behaviour (Button, Input, Textarea, Select→`Listbox`, Modal→`Dialog`, Popover→`Dropdown`, Drawer→mobile sidebar). Style it by replacing its override slots with `slot()` from `src/lib/baseui.tsx`, which renders Tailwind classes and maps BaseUI `$` state props to the `data-hover`/`data-active`/`data-focus`/`data-disabled`/`data-invalid`/`data-closed` attributes our classes target. Plain links and buttons get the same attributes from `useInteractive` (`src/lib/interactive.ts`). Do not style BaseUI with `style` overrides except to neutralise a surface (`transparentSurface`).
   - Icons are Heroicons (`@heroicons/react/16|20/solid`), which carry `data-slot="icon"` for the Tailwind icon styles.
   - Pass `className` for placement and spacing; components merge it before their own classes, so don't pass utilities that compete with them. Map variants/colours to complete class strings so Tailwind can detect them.
   Keep layouts responsive and retain keyboard navigation, focus indicators, accessible names, labels, error/status announcements, and reduced-motion support.
7. Keep the server free of user data: there is no server rendering, and prerendered pages are built without a session. Go sends signed-out requests for `/app/*` to login before serving any HTML; signed-in pages load the session in the layout route's `clientLoader` and their data through SWR (instant page swaps with skeletons). Never cache user data in module-level variables. Styletron CSS for prerendered pages is collected per file at build time (`entry.server.tsx`). SWR keys include user ID. The app shell and API responses must remain no-store.
8. Every async interaction must handle pending, success, failure, and empty results. Disable duplicate mutation submission; use `<Button loading>` for pending actions, `ListSkeleton` for fetched lists, and route progress. Preserve available data on a refresh failure and provide Retry. Redirect expired sessions to login.
9. Persist real application data through the Go API. Derive dashboard counts from actual project data. Demo records belong in the explicit seed command, never hardcoded in UI. Registration never creates or joins a workspace, and new accounts have no projects. A new account goes to onboarding to create its first workspace, unless it signed up through an invitation link; it then returns to that link, which accepts the invitation. Joining a workspace only ever happens by accepting an invitation link: never look up invitations by email at sign-up or sign-in, and never treat an invitation link as verifying an email (`docs/api/auth.md#email-verification`).

## Authentication/security invariants

- Keep Argon2id with fresh random salts and constant-time comparison. Never log/store plaintext passwords. Password minimum at sign-up is 12 Unicode characters, max 128 UTF-8 bytes; login checks only the max, so the development seed's `DEMO_PASSWORD` may be short (`password`).
- Opaque 256-bit server sessions, digests in DB, independent CSRF tokens, HttpOnly/SameSite cookies; production Secure `__Host-` cookie. No session or CSRF tokens in localStorage, URLs or query strings. The one exception is single-use emailed link tokens (password reset, invitations): they may appear in their page's path, and in `?next=` pointing at that page (`returnPath` matches the exact token shape). They are never put in API URLs; they go in JSON bodies.
- Enforce exact Origin, content type, and CSRF for mutations; keep rate limits (budgets in `RequireSession`, feature limits, auth limits) and quotas, hashing concurrency bound, session rotation, idle/absolute expiry, logout revocation, and other-session revocation.
- Require session middleware on every private endpoint. Workspace data goes through `RequireWorkspace` (membership via `workspace_user`, same 404 for non-members and missing workspaces) and every workspace mutation names its permission with `ws.Can` (`internal/auth/permissions.go`; the `ws` group panics on an unguarded one); scope SQL by the member's workspace ID, never a request-supplied owner, workspace or role. Test non-members, other workspaces and refused roles before adding resources.
- The admin dashboard (`docs/api/admin.md`) is the one place queries cross workspaces, so every `/api/admin/` route is registered in `adminRoutes` behind `RequireAdminKey` (`RequireAdminKeyOrPrevious` for those behind a session; a wrong or missing `X-Admin-Key`, or an address outside `ADMIN_ALLOWED_IPS`, answers exactly as an unknown route, before anything else) and, apart from the sign-in steps, `RequireAdminSession` (a separate table and Strict cookie; an app session never counts; a session works only under the key it was made with, and `ADMIN_ROUTE_KEY_PREVIOUS` never opens the sign-in). The key travels only in the page URL and `X-Admin-Key`, never in an API path, storage, SWR keys, page text or a log. Admin and an admin's role (`viewer`, `operator`) are granted only from `cmd/admin`, never through the API, a page or a seeder; every admin must have MFA (set up at the door only inside the window `grant` opens) and can't turn it off; every admin sign-in takes the password and a code. Every admin route that changes anything names the role it needs with `Role` (`RequireAdminRole`; the signed-in group panics on an unguarded mutation), apart from the sign-in steps and the admin's own sessions (`OwnSessions`: signing out, and out of their other sessions). Every account-and-access action (unblocking an address, signing an account out, resetting its MFA, suspending it, revoking a workspace's invitations, retrying deliveries, IP blocks, signing another admin out: `docs/api/admin.md#actions`) needs the `operator` role, a fresh code (`RequireAdminStepUp`: a 5-minute window `POST /api/admin/step-up` opens with a code checked as at the door) and a reason of 10 to 500 characters, counts against `admin-action:per-user` (all three from `Action` in `adminRoutes`; `Role` with `operator` panics on any other mutation, and `Housekeeping`, the operator-only tier without a code, takes only its listed routes), and records one `admin.*` event with the admin and the reason in the change's transaction; a session's fifth wrong step-up code ends it. Never on the acting admin's own account, and never on another admin apart from signing them out: suspending an admin or resetting an admin's MFA is the command line's. A suspended account never has or gets a session (app or admin), gets no reset link, and hears why only after its right password and code. Every admin read is recorded (the one exception: the catalogue of names the filters offer).
- Identify records outside the API only by their public IDs (`usr_`/`wsp_`/`prj_`/`inv_` + 14 base62, generated by the PostgreSQL `public_id()` column default); never expose internal bigint IDs in responses or URLs.
- Log only through the handler every command installs (`internal/observe`), with `slog.*Context(r.Context(), …)` during a request so the line carries its `requestId`. Never log a request's path, query string, headers, cookies or body: they hold link tokens, the admin key, CSRF tokens, searches and emails. The access line names the matched route pattern or a fixed page label, never the path; a 500 answers only the generic message and the request's ID (`httpapi.InternalError(w, r, err)`), and a panic is recovered into the same, its value logged only through `observe.PanicValue`. The request ID is always the server's own, never taken from a request. An error's text can quote personal data (a database or SMTP error naming an email or a typed value), so log an error only as `observe.ErrorAttr(err)` (scrubbed by `observe.Scrub`), never `"error", err`, and store one only scrubbed (`event_deliveries.last_error`, `app_errors`); scrubbing is a backstop, so never build an error or panic message from a secret. Failures worth counting go to `observe.Report`, which groups them in `app_errors` (a row per fingerprint, never per occurrence); a client that went away (`httpapi.ClientGone`) is no error. `POST /api/client-errors` takes the signed-in web app's own errors with a route pattern, never a URL, outside the write budget with its own `client-error:per-user` and `client-error:global` limits; its text is scrubbed as a browser's (`observe.ScrubClient`), and an admin page showing it must label it as user-reported and never link it (`docs/api/observability.md`). Metric labels come only from fixed sets (route patterns, limit, listener and event names, status classes), never from a request, and each metric is capped; the database gets per-minute sums per route (`request_minutes`, insert only, never retried), never a row per request; `/metrics` runs only on its own listener (`METRICS_ADDR`), behind `METRICS_TOKEN` on any public bind; a slow query is logged without its text or values; the configuration summary in `server_instances` never holds a secret's value or digest.
- Pass every value through Bun `?` placeholders (Bun escapes them into the query) and never build SQL text from input. Use bounded bodies/fields/headers, HTTP/query timeouts, generic public errors, and graceful shutdown. Do not enable wildcard credentialed CORS. Believe a forwarded client address only through `httpapi.ClientIP(r)`, which reads `CLIENT_IP_HEADER` only on connections from `TRUSTED_PROXIES`.
- Keep script CSP hashes for the built HTML (computed by `internal/web` at startup from each file's inline scripts; never `'unsafe-inline'` scripts) and the other security headers; inline CSS is required by Styletron. Production requires HTTPS and verified DB TLS. No demo seed in production.
- See `docs/api/auth.md` for limits. Password reset links and workspace invitations are emailed over SMTP (`MAIL_DRIVER=smtp`, the default everywhere: a server without SMTP settings refuses to start unless `MAIL_DRIVER=off`, which also needs `EMAIL_VERIFICATION=off`). Production requires `SMTP_TLS` `starttls` or `tls` with verified certificates; `none` is for the local Mailpit only, and the `log` mailbox file is refused in production. Every email someone can trigger needs a `<feature>:per-email` limit on its request (the one cap in a listener, `account-exists:per-account`, exists because a limit on the request would reveal which emails have accounts); security mail is never limited; workspace notifications must be opt-in, never automatic (`docs/api/mail.md`). Two-factor authentication exists as authenticator-app codes (TOTP) plus single-use recovery codes, optional per account; its secrets are sealed with `APP_KEY` (required everywhere; changing it locks out every account with MFA on), and a code or the password alone never turns it off: the account turns it off with both, and only an operator resets it for someone who lost both, from `cmd/admin reset-mfa` or the dashboard's Reset two-factor authentication (an `operator` admin's fresh step-up code, a written reason and the out-of-band confirmation of who is asking, recorded; never an admin's from the dashboard). Email verification exists (`EMAIL_VERIFICATION`, on by default: a 6-digit code at sign-up before the account exists, from Account settings for older accounts, required at sign-in with `EMAIL_VERIFICATION_EXISTING=required`); sign-up must answer the same, and do the same work, whether or not an email has an account. Do not claim passkeys, OIDC or changing an account's email exist until they are implemented and tested.
- A blocked email address (`docs/api/auth.md#blocking-an-email-address`) gets no email at all (every `mailer.Send` checks the block list) and can't become an account (checked under `database.LockEmail` wherever a user is created). Only an address without an account can be blocked, and only through the block link emailed to it; nothing anyone types (inviting, signing up) may reveal that an address is blocked; the command line and the admin dashboard (an operator, behind a fresh code and a reason) can only unblock.
- Email goes through `mailer.Send` (`internal/mail`) from a listener, never a handler, rendered from embedded `html/template` files; never `text/template` for HTML, never wrap data in `template.HTML`/`template.URL`, and never put user data in mail headers.

## Database and migrations

- Read `.env` (untracked); `.env.example` is a local test template. Do not commit production secrets.
- The supplied local test DB is `postgresql://lewcontext:password@127.0.0.1:5432/lewcontext` (local setup adds `sslmode=disable`). Use only for development/testing.
- Forward/reverse migrations are Bun SQL pairs under `apps/api/migrations` named `<version>_<name>.tx.up.sql` / `.tx.down.sql`; one create migration per table. **While in development, migrations are squashed:** change a table by editing its create migration, then rebuild the local database with `make migrate-fresh CONFIRM=1 && make seed`. Once a database holds data that must be kept, migrations become append-only again (never rewrite applied ones). The Bun migrator (`internal/database/migrate.go`) runs each file in a transaction, records it in `bun_migrations` only after success, groups each run for rollback, and holds a PostgreSQL advisory lock. No auto-migrate on API startup.
- Do not drop/reset databases or existing app data, except the local development database with `make migrate-fresh` (previews without `CONFIRM=1`, refused when `APP_ENV=production`), and an e2e run's local `*_test_<port>` database, which `make serve-test` rebuilds on every start. Integration tests create and remove only their unique temporary schema in `lewcontext_test`. Down migration SQL is destructive and requires explicit user authorization; `make migrate-rollback` only previews unless `CONFIRM=1`. `make prune` deletes old rows from log tables (the `events` audit trail, `app_errors`, the hourly metric sums `request_hours` and `metric_hours`) only with a target and `CONFIRM=1`, never under an hour old, and keeps events whose deliveries are pending; it is allowed in production (cron).
- The idempotent demo seed is explicit. It creates only its demo user, the "Acme" workspace, its projects and four fake `@example.test` members with unusable passwords, and leaves an existing account unchanged. Other seeders (`make seed only=volume|users`) only insert fake data; seeders live in `internal/seed`.
- Write every query with Bun's query builder (`NewSelect`, `NewInsert`, `NewUpdate`, `NewDelete`, `With`, `Where`/`Set`/`ColumnExpr` with `?` placeholders), in application code and tests alike. Don't write SQL strings with `NewRaw`, `QueryContext`, `QueryRowContext` or `ExecContext`. The only exceptions are statements Bun has no builder for in `internal/database` (creating and dropping schemas, advisory locks) and the migration `.sql` files.
- Every table has a factory in `apps/api/internal/factory` with its own Bun model. A migration that adds a table or a required column updates the factory (and seeders) in the same change; `TestEveryTableHasAFactory` enforces this. Integration tests build data with factories rather than hand-written rows or setup through API calls, except where the endpoint itself is under test.

## Commands and validation

Use `make db` (PostgreSQL with pgvector, and Mailpit, the local inbox at `http://localhost:8025`, in Docker), `make install`, `make migrate` (`make migrate-status` to inspect), `make seed`, then `make dev` (`scripts/dev.sh`: the API and two Vite servers in one terminal, Vite on :3000 proxying `/api` to Go and `/admin`, `/admin-assets` to the admin build's Vite on 127.0.0.1:3002; or `make api`, `make web` and `make web-admin` in separate terminals). `make serve` instead builds the single binary with the web app embedded and runs it on :3000, as in production. `make docker-dev` runs the whole app in Docker from the `Dockerfile` instead (database, image build, migrate, seed, then the app); after a code change, `make docker-app` rebuilds and restarts only the app container. Make loads root `.env`. Browse `http://localhost:3000` with the default origin configuration.

Before claiming completion, run relevant checks and report failures:

- `make test` and `make check`. `make check` also checks the docs' relative links and anchors (`scripts/check-doc-links.mjs`); fix a dead link or anchor rather than ignoring it.
- `make test` includes the PostgreSQL integration tests (auth, SQL, migrations, middleware, authorization) and fails without the database (`make db`). Tests read the committed `.env.testing`, never `.env`; keep only local, throwaway values in it.
- `make test-e2e E2E_PORT=auto` for user flows (it covers the Go page gate and CSP, which the Vite dev server doesn't have). Playwright builds and starts the server on its own port and database (`lewcontext_test_<port>`); use the URLs and database it reports. Default installed Chromium path can be changed with `CHROMIUM_PATH`.
- `make build` when changing frontend/build integration or backend composition.
- Check dependency audits for dependency/auth changes. Preserve lockfiles. Explain compatibility overrides in `docs/ui/README.md` (Dependencies); do not suppress type errors with `any`/unsafe casts instead of fixing dependencies.
- Do not add tests that merely mirror trivial styling. Prefer behavior, security boundaries, and real persistence coverage.
