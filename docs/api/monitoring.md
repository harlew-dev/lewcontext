The app already records what an operator needs to spot trouble (every sign-in attempt and its result, every limit reached, request rates and latency, grouped errors). These pages turn each of those into a **signal**: a number with the levels at which it's a problem, a chart over time, and a link to the rows behind it. The dashboard runs inside the app it watches, so it can't say the app is down; an external uptime check does ([deployment.md](../deployment.md#logs-and-health-checks)).

## How every page works

- **One endpoint per page:** `GET /api/admin/monitoring/{page}?window=1h|24h|7d` (default `24h`), `admin.Monitoring.Show`, behind the admin key and an admin session like every admin route ([admin.md](admin.md#api)). `{page}` is one of the pages built (`monitor.PageNames()`: `overview`, `security`, `limits`, `ips`, `accounts`, `workspaces`, `usage`, `data`, `integrity`, `performance`, `errors`, `configuration`); any other is 404 "Page not found.", an unknown window 400 "Check the window.", any other parameter (or one given twice) 400. Viewers read every page: nothing here changes data.
- **One recorded read per page:** `admin.monitoring.viewed` (`admin`, `page`, `window`), actor only, written once the page was read, so a page's signals, charts and review lists are one read. A page that wasn't served (busy, too slow, an error) records nothing, since nothing was read. One address's page is its own read, `admin.ip.viewed` ([below](#one-address)), and so is one error group's, `admin.error.viewed` ([below](#one-group)).
- **Bounded:** a page is a set of aggregates, so it shares the Events charts' bound (`httpapi.Summaries`, [admin.md](admin.md#the-summary)): **one page or chart summary in flight per admin**, **two at once per server** (waiting at most 1 s for a slot), and a **5 s deadline** for the whole page. Within it, **each signal and each section has a budget of its own** (2 s, `Summaries.Section`; `monitor/sections.go`): one that isn't read in time is sent as not loaded (a signal with `unavailable: true`, a section's key in the answer's `unavailable` list, its data missing) and the rest of the page still answers, so a slow query, or one someone's own events slow down, hides its part and never the page (`TestAdminMonitoringSectionsFailAlone`). Past the slot it answers `503` "Monitoring is busy. Try again in a moment." (with `Retry-After: 1`); only when nothing at all could be read in time, `503` "This page took too long. Try a shorter window." `admin-read:per-user` still counts the request once. Every query is bounded by a window of 7 days at most (the review lists' takeover lookback reads one account's own sign-ins through its index), read through an index, and returns at most 20 rows per review list.
- **Computed when read** (decision 3), never stored. A signal too slow at real volume moves to the hourly rollup ([observability.md](observability.md#metrics-in-the-database)), not to a slower page.
- **SQL:** every query is Bun's builder in `internal/store/monitor_*.go`, values through `?` placeholders. Pages, windows, signals, limits and outcomes come from fixed Go tables; nothing from input becomes SQL text.
- **Emails and IPs only in review lists** (decision 7): the Security page's lists name the addresses and emails behind an attack, Rate limits' top addresses the addresses reaching the most limits, and the IP addresses page and one address's page the addresses events came from, admin-only and recorded; everywhere else is counts (the Accounts, Workspaces and Usage pages name accounts and workspaces by ID and name only, and one address's page counts the emails it tried that have no account, never naming them). An account is named by its `usr_` ID and name, never its email. No response holds a token, hash or internal ID (`decodeAdmin` walks every one in the tests).

### The response

```json
{
  "page": "security",
  "window": { "name": "24h", "from": "2026-10-31T14:30:00Z", "to": "2026-11-01T14:47:12Z", "bucketSeconds": 1800 },
  "signals": [
    { "name": "auth.failed_sign_ins", "label": "Failed sign-ins", "unit": "count", "value": 1204, "sample": 1204,
      "level": "critical", "warn": 100, "critical": 1000, "windowSeconds": 3600,
      "drill": { "name": "auth.login_attempted", "outcome": "failed", "window": "1h" } }
  ],
  "sections": { "…": "the page's own" },
  "unavailable": []
}
```

- **The window** is resolved by the server, like the Events page's (`monitor.ResolveWindow`; `TestMonitorWindowsMatchEvents` keeps them equal): it starts on its first bucket's boundary and runs to now. Buckets: 1 minute for `1h`, 30 minutes for `24h`, 3 hours for `7d`. Charts list every bucket, empty ones as zeros.
- **Signals keep their own windows** (an hour, a day, or "now"), whichever window the charts show: a signal says how things stand now, the charts how they got there. Each carries its `value` in its `unit` (`count`, `percent`, `ms`, `minutes`, `per_minute`, `bytes`), the `sample` it was counted from, its `level`, its thresholds and `minSample`, its window in seconds, and `drill`, the Events page's filter for its rows (`name` tokens, `outcome`, the `window` of the same length) when it has one.

## Signals (`internal/monitor`)

Each signal is defined once, in Go (decision 2): its name (stable: alerts and these docs use it), its page, label, unit and window, its **warn** and **critical** thresholds (0: no such level), an optional **minimum sample** (below it the level is `ok` whatever the value: a share of a handful means nothing), how it's measured (a store query), and its drill-down. **A value at or over a threshold is at that level**, the higher winning. Thresholds change only by a reviewed commit, and this table with them. **Anyone with an account can raise a level**: their own wrong passwords, codes and password checks, junk emails at sign-in, limits they reach on purpose. A level says something is happening, not that it's an attack on someone else, so the [alerts](#alerts) that read these allow for a level raised on purpose, to cry wolf or to hide something else in the noise. Alerts read the same definitions.

A signal's span is its window before now, its start floored to the window's bucket as the Events page floors the same window (an hour to the minute, a day to 30 minutes), so its drill-down covers the rows it counted (and any recorded since). **Only some drill-downs list exactly the rows counted** (`drillExact: true`): failed sign-ins, the unknown-account share (the attempts it's a share of), limit windows reached and sign-ups. The others list the events the number was counted from, which is more: stuffing and guessing (every attempt in the hour, not only the address's or email's), success after failures, takeovers (every such change), failed codes and password checks (every failure, not only the accounts' at 3+), the reset and shared limits (every `rate_limit.reached`), the sign-up limit, and the admin door (its failures' list holds the refusals of real credentials too, and the refusals' list the wrong passwords: the Events page has no filter for one result). The Events page has no filter that would make them exact, and none was added for it. `TestSignalsAreWellFormed` checks names are unique, every drill-down names only catalogue names or groups and a window the Events page takes, and warn is below critical.

## Overview

A grid of tiles, each an area with one or more signals: its worst level in words, its first signal as the number, the others listed under it with their levels, a sparkline over the page's window, and a link. Tiles: **Servers** (live, versions), **Requests**, **Server errors**, **Latency**, **Database** (round trip, minutes with pool waits), **Data** (the database's size, prune targets not running, targets past their retention; a sparkline of events recorded per bucket, from `events_created_idx` alone), **Mail** (oldest waiting, failed), **Errors** (new, new panics, open), **Integrity** (critical and warning checks failing), **Failed sign-ins**, **Shared limits**, **Admin door** (refusals, failures), **Sign-ups** (sign-ups, active accounts).

- **Read order:** the Integrity tile's summaries are read after every other tile's signals (they run every check, the page's costliest reads), so a slow check uses up their own budgets and never the security tiles'. A partial summary says how many checks it read.
- **Links:** every tile links to its page (Configuration, Performance, Data, Errors, Integrity, Security, Rate limits, Usage), Mail to the Mail page. **Alerts** has no tile: its count is the sidebar's. With metric storage off on every live server (`metricsStore: "off"` in the answer, from the servers' summaries), Requests, Server errors and Latency say "Metric storage is off.": zero there isn't no traffic.
- **Sparklines:** connections in use (the pool gauge's average per server) per bucket; requests, 5xx share and p95 per bucket from the request minutes (over 7 days, the hours summed so far and the minutes after them, so nothing is counted twice: `requestRows`); failed sign-ins, shared limits reached, the admin door's failures and refusals, and sign-ups per bucket from events.

## Security

From `auth.login_attempted`, `auth.mfa.checked`, `auth.password_checked`, `auth.password_reset.*`, `auth.registration.requested`, `auth.registered`, `auth.logged_in`, `admin.login_attempted`, `admin.access_refused`, `admin.session.moved`, the takeover changes, `rate_limits` and `sessions`. Every review list groups by the hour from the window's start ("in an hour"), at most 20 rows:

| Section | Shows |
| --- | --- |
| Sign-in attempts | per bucket by result (signed in, right password and a code asked, wrong password, unknown account), and the share for unknown accounts |
| Credential stuffing | hour, address (linking to its sign-in attempts), distinct emails, attempts, how many signed in |
| Distributed guessing | hour, email (linking to its events), distinct addresses, failures |
| Success after failures | account, wrong passwords, when it signed in |
| Possible takeovers | one row per account (its newest such change, so one account can't fill the list): account, the new network, the sign-in, the change (linking to its event) |
| Second factor | accounts failing 3+ codes in an hour; recovery codes used; accounts left with 2 or fewer after using one (the payload's `recoveryCodesLeft`) |
| Password checks | accounts failing 3+ password checks in an hour |
| Password resets | asked for against sent per bucket (a gap is someone trying addresses), the addresses asking most, `password-reset:global` against its cap |
| Sign-ups | codes asked for and accounts made per bucket, the addresses making the most accounts, `register:global` against its cap |
| Admin door | counts per outcome (wrong password, unknown account, not an admin, admin without MFA, address not allowed, session moved), per bucket as failed sign-ins, refusals and moved sessions (three series: a chart stacks five at most, which `TestAdminMonitoringPages` checks for every chart), and the latest 20 with time, outcome and address (never the email typed), each linking to its event |
| Sessions | sign-ins per bucket, live app sessions, accounts at the 5-session cap |

**Indexes:** `events_name_created_idx (name, created_at DESC)` finds every name in its window; the takeover check looks only at the accounts that made a takeover change in the window (`events_name_created_idx`), starts from their sign-ins in the window (and the hour before), keeps those from a new network by comparing each with **the account's last 50 sign-ins** in the 30 days before it (one range of `events_logged_in_idx (user_id, created_at DESC) INCLUDE (ip) WHERE name = 'auth.logged_in'`, read from the index alone), and only then looks up the account's changes in the hour after each (`events_user_created_idx`). So an account recording thousands of its own changes doesn't slow it (`TestAdminMonitoringTakeoverFlood`), and nor does one signing in from a new network every time: each sign-in costs at most 50 index entries, where comparing with every earlier one was quadratic (6,720 such sign-ins took 6.2 s over a week; `TestAdminMonitoringTakeoverNetworks`). `sessions` holds live sessions only (the cleanup).

**What the takeover check can't see** (for [alerts](../../plans/features/implemented/admin/alerts.md) or a later plan): a change made **more than an hour after** the sign-in from the new network, and a takeover from a network the account **signed in from once before** in the 30 days (the attacker's first sign-in makes the network known, so a change after a second one isn't flagged). Tying each change to its own session's sign-in network would close both, but neither a session nor an event records the session it came from, so it needs a column of its own (`sessions.ip` or an event's session) and isn't built.

## Rate limits

A limit **reached** here is its block level, where it refuses requests: every `rate_limit.reached` query on these pages (the signals, the charts, the top accounts and addresses) keeps `<name>:block` only (`store.blockReached`). A challenge level crossed (`auth:per-ip:challenge`) only asks for a CAPTCHA, and `register:global`'s at 200 an hour is an ordinary busy hour; those crossings are on the Events page, and their 428s in Requests refused.

| Section | Shows | From |
| --- | --- | --- |
| Shared limits | every `*:global` limit: what counts toward its cap (its block level) in its live window (a meter with its level: half used a warning, reached critical; the answer also carries its challenge level, `challenge`, 0 without one), when the window ends, and how often it was reached in the page's window. Above a challenge level with a CAPTCHA provider only the requests that passed count toward the block level (the challenge level's worth plus the `<name>:passed` counter; [rate-limits.md](rate-limits.md)), so that's what the meter shows (`towardBlock`); without that counter, the limit's hits | `rate_limits` (keys are the bare name, and `<name>:passed`), `rate_limit.reached` |
| Windows reached | per bucket by limit (the four reached most, then Other), and per limit with the last time. A window reached is counted once, however many requests it then refused | `rate_limit.reached` |
| Requests refused | every refusal per limit and level: `<name>:block` (429 or 503) and `<name>:challenge` (a 428 asking for a CAPTCHA, or a 503 while the provider can't be reached) | `rate_limit_refused_total` in `metric_minutes` (and `metric_hours` over 7 days) |
| Blocked right now | per limit counted by subject, how many subjects are at or over its block level in their live window. Keys are digests: how many, never who. A limit counted in each server's memory (`api-read:per-user`, `admin-read:per-user`) can't be seen, and says so | `rate_limits`, keys split on the name, compared with the limits declared in Go |
| Accounts / addresses reaching the most | top 10 by windows reached | `rate_limit.reached`'s `user_id` and `ip` |
| Budgets | accounts reaching `api:per-user` or `api-read:per-user`: a script, a scraper or a runaway tab | `rate_limit.reached` |
| Quotas | refusals per quota | `quota_refused_total` |
| By route | routes answering 429, with requests and 5xx (a shared limit's 503 counts among them: `request_minutes` doesn't keep 503 apart) | `request_minutes` (and `request_hours`) |

### One address

`GET /api/admin/ips/{ip}?window=1h|24h|7d` (`admin.IPAddresses.Show`): an IP address (an IPv4-mapped one as IPv4, never with a zone) or an IPv6 /64, its slash escaped (`2001:db8::%2F64`); anything else is 404 "Address not found." (`monitor.ParseAddress`). Bounded like a page (one per admin, two per server, 5 s) and recorded as **`admin.ip.viewed`** (`admin`, `address`, `window`; the address looked at is `address`, apart from the event's `ip` column, which is the admin's own): looking an address up is following someone. A refusal or a busy read records nothing. It answers, over the window and through `events_ip_created_idx` (`ip <<= ?`): the events and when the address was first and last seen in it, its events by name, the accounts seen from it (signed in, made there, failing to sign in; at most 20, by ID and name), **how many** different emails with no account it tried (never which: its events show them, a recorded read of their own), the limits it reached, and for a /64 its addresses (at most 20), and the live IP blocks holding it or part of its /64 (`blocks`: `network`, `expiresAt`; the page shows them in a warning with a link to the IP blocks page). An IPv6 address's answer names its /64 (`network`) to open. Everything recorded from the address counts here, admin reads included. ## Errors

The grouped errors (`app_errors`) **last seen in the window**, newest occurrence first, at most 50 (`app_errors_last_seen_idx`; the table holds at most 1,000 groups between flushes and is pruned 30 days after a group was last seen): source, route, the scrubbed message, the count since first seen, first and last seen. The server sets each group's `new`, comparing the times (never their text, whose offsets may differ). **A browser's group** (`source: client`) is labelled **User-reported** and its text, like every group's, is shown as text, never a link: someone could write it. Occurrences per bucket by source come from `errors_total` (nothing with metric storage off). Read-only: resolving a group is an admin action (A6), marked in the pages.

### One group

`GET /api/admin/errors/{error}?window=1h|24h|7d` (`admin.Errors.Show`): an `err_` ID (`app_errors.public_id`, a column default); any other shape, or none, is 404 "Error not found.". Bounded like a page and recorded as **`admin.error.viewed`** (`admin`, `error`, `window`); a refusal or a busy read records nothing. It answers the group with its latest occurrence's **stack** (scrubbed: function names, files and lines), `lastRequestId` (to search the logs with: always ours), **`lastVersion` only in a release's shape** (`store.ReleaseShape`: a revision, `-dirty`, or `dev`; anything else is empty), the release now running, and its **route's occurrences** per bucket (`errors_total` counts by source and route, so every group on the route). "Versions seen" (the plan) isn't kept: a group keeps only its last version.

## Active accounts: `users.last_seen_at`

`users.last_seen_at` is when the account last used a session, to the hour. The session check (`store.FindSession`, behind `RequireSession` and the `/app/*` page gate) moves it **in the same statement** that refreshes the session's idle time, and only when it's null or over an hour old (`seenEvery`), so an active account costs one row write an hour and the check no extra round trip. It never records an event: it isn't something the account did, and an event an hour per account would fill the audit trail. It's null until the account's first signed-in request; an expired or idle session, or a suspended account's ([admin.md](admin.md#suspending-an-account): the same statement doesn't find its session), moves nothing. It never waits for the account's row (`FOR NO KEY UPDATE SKIP LOCKED`): changing the password or making a session locks the account and then its sessions, the other way round from the session check, so waiting could deadlock; a locked account's time just moves on its next request (`TestSessionCheckSkipsALockedAccount`). A partial index (`users_last_seen_idx`) serves counting the accounts seen since a time. `TestSessionCheckMovesLastSeenHourly` (`internal/store`) checks it, a suspended account's session included.

**Before migrations become append-only:** the column is edited into `002_create_users` while migrations are squashed, so every database rebuilt since has it from an account's first request. A database that gains it by a migration instead starts with it null for every existing account, which the inactive-accounts list reads as "never seen" (`coalesce(last_seen_at, created_at)`), so an old account active yesterday would look inactive. That migration needs a backfill first: each account's newest `sessions.last_seen_at` or `auth.logged_in` event (kept 90 days), whichever is later.

## Alerts

Code: `internal/alerts` (`evaluator.go`, `runner.go`, `listeners.go`, `webhook.go`, `outbound.go`, `format.go`), `internal/monitor/alerts.go` (the rules), `internal/store/alerts.go` and `admin_alerts.go`, `internal/database/lock.go` (the locks), `internal/httpapi/endpoints/admin/alerts.go`, `alert_silence.go` and `me.go`, `internal/mail/templates/alert*.{html,txt}`, `cmd/server/alerts.go`. Web: `pages/admin/[key]/alerts/index.tsx` and `alerts/[alert].tsx`, `components/app/admin/alerts.tsx`. Plan: [alerts](../../plans/features/implemented/admin/alerts.md) (A5).

A dashboard only helps when someone looks at it, so a signal that stays at its warning or critical level **opens an alert**, which reaches admins by email and an optional webhook within minutes. An alert is a monitoring signal ([Signals](#signals-internalmonitor)) with a rule (`monitor.AlertRules`), so a page and its alert always agree.

```
every minute, on one server (the leader)
  for each rule: read its signal ──▶ level ok / warn / critical (the rule may narrow it)
  not ok for the rule's For ──▶ open an alert (alert.opened); raise a warning to critical in place (alert.escalated)
  ok for 10 minutes ──▶ resolve it (alert.resolved)
  every hour: the integrity rules, the same way
  a critical alert still open, unacknowledged and not silenced, 4 hours after its last email ──▶ alert.reminded
  openings past the burst limit ──▶ one digest (alert.digested)
  then GET ALERT_HEARTBEAT_URL, if the evaluation worked

alert.* events ── listeners (the delivery queue and its retries) ──▶ email to admins (mail.alert*)
                                                                └─▶ webhook (alert.webhook*)
```

### One evaluator across servers

Every `cmd/server` runs the loop (`alerts.Runner`), but each minute only the process holding a PostgreSQL **session advisory lock** evaluates (`database.TryLeadAlerts`: `pg_try_advisory_lock` on a connection of its own, keyed by a hash of a fixed name and the schema, never waiting). Others stand by and try again the next minute. The lock ends with its connection, so a server that dies hands it over within a minute; a server that stops releases it at shutdown (`Runner.Release`, before the database closes); and a leader that finds its lock gone (`Leader.Check` reads `pg_locks` each turn, within 5 seconds: a connection that hangs counts as lost and is closed) lets go and stands by, forgetting what it remembered (an alert's `For` and its time back at ok), so the new leader delays an alert at worst and never doubles one. Backstops: every change to an alert takes a transaction lock (`database.LockAlertWrites`) before it reads what it decides by, and the unique index `alerts_open_signal_idx` allows one open alert per signal, so even two evaluators at once could neither open nor tell about the same thing twice. The leader's evaluation has a 30 s deadline.

The plan's "A server silent for 2 minutes" and "oldest event older than 97 days" rows have no signal to alert on yet (a stopped server's row stays a day, so the live count can't say "silent"; the Data page, built later, owns retention) and are left out; `servers.versions` isn't a rule because `integrity.servers_out_of_step` already waits out the release's 30 minutes. `TestAlertRulesAreWellFormed` checks every rule names a signal with a level to alert at, a sentence of meaning and no duplicate.

### When an alert opens, and who is told

- **Opening** records `alert.opened` (no actor, the signal's name, level and value) in the transaction that inserts the row, and decides there how it is told (`alerts.notified`), so a delivery that runs again or late decides the same: `mail` (emailed and posted), `held` (the burst limit: waiting for a digest, posted), `digest` (in a digest), `quiet` (nobody).
- **Bounds against floods.** One open alert per signal, however long it lasts. A signal that opened an alert within the last hour (`store.AlertCooldown`) opens its next one `quiet`, and **a quiet alert's escalation and resolution tell no one either** (no email, no webhook): a flapping signal, or someone raising a level on purpose again and again (warn, critical, ok, warn…), is told about once an hour at most. **Every email about an alert counts** (each alert keeps when its emails went, `alerts.mail_times`): one signal's alerts send at most 3 emails an hour of every kind (opening, escalation, resolution, reminder: `store.MaxSignalMails`), and anywhere in the system more than 5 emails within 10 minutes (`AlertBurst`, `AlertBurstWindow`) make an opening a digest email (at most one every 10 minutes, the others held), while an escalation, resolution or reminder past that is simply not emailed (the dashboard and the webhook still say). A critical alert still open, not acknowledged and not silenced is emailed again every 4 hours (`AlertRemindEvery`); warnings are never reminded. Escalating to critical emails once more, in place, whatever the opening was.
- **Silenced** (below): nothing is emailed or posted for the alert or for another alert of its signal opening meanwhile (`runningSilence`: the silence is carried to the new alert), and listeners check again when they run, so a silence set after an event was recorded still holds.
- **Resolving** emails again those admins whose alert was emailed, and posts, unless silenced.

### Email to admins

Operational mail to the people who took the admin role, not a workspace notification: each admin's own `admins.alert_email` is the opt-in (`all`, `critical`, the default, or `none`), set by that admin on the Admins page (`PATCH /api/admin/me {alertEmail}`, any role, no code: it changes only their own inbox; recorded as `admin.updated` with `changes.alertEmail`). It's triggered by no request, so there's no per-email limit; the bounds above stop a flood. Listeners (`alerts.Listen`): `mail.alert`, `mail.alert_escalated`, `mail.alert_reminded`, `mail.alert_resolved` and `mail.alert_digest`, each sending through **`mailer.Send`**, so the email block list holds (`ErrBlocked` is done). One admin's refusal doesn't hold up the rest; when some sends fail and some succeed, the failures are logged and reported as an error group and the delivery is done (a retry would email the others twice); when all fail it is retried like any email.

**Content (decision 6):** fixed text and numbers only: the signal's title, the level's word, its value in its unit, when it opened (UTC), how long it was open, and one sentence of what it usually means. Never the admin key, a link of any kind (the email says "Open the admin dashboard"), an email address, an IP, an account or workspace name or a sample ID: those stay in the dashboard. Templates `alert` and `alert-digest` (`html/template`; the plain text separately), the subject built in Go from the signal's title (`AlertData.Subject`, checked against a strict shape by `mail.subjectOf`: `"Critical alert: …"`, `"Warning: …"`, `"Now critical: …"`, `"Still open: …"`, `"Resolved: …"`); a rule's `Title` replaces a label that only reads on its own page. `TestAlertContentHoldsNoSecretsOrPersonalData` renders every kind for every rule's signal, a digest, and the webhook's bodies in both formats, with an alert whose details hold an account's ID and email, and fails on the admin key, the origin, any URL or `href`, an email address, an IP, an ID or a name.

### Webhook

`ALERT_WEBHOOK_URL` (optional) gets every alert event as a `POST`, from the `alert.webhook*` listeners, so retries and failures are in the Mail page's queue (the same 1 s … 1 h schedule). `ALERT_WEBHOOK_FORMAT`: `json` (default) `{alert, event, state, signal, title, level, value, unit, openedAt, resolvedAt, meaning}`, or `slack` (`{text}` with Slack's escaping of `& < >`; the many tools that accept Slack's incoming-webhook shape). `ALERT_WEBHOOK_SECRET` (32+ characters, optional) signs the body: `X-Lewcontext-Signature: t=<unix seconds>,v1=<hex HMAC-SHA256 of "t.body">`, so the receiver can check it's ours and refuse an old body played again. The body holds what an email does, nothing more. **`X-Lewcontext-Delivery: evt_…`** names the event being posted and is the same on every retry of it, so a receiver can drop a body it has seen (the signature's time only bounds how old a replay can be).

### Heartbeat: watching the watcher

`ALERT_HEARTBEAT_URL` (optional) is `GET` by the leader after each evaluation that worked (so nothing is pinged when the evaluation fails or no server leads): a dead man's switch for Healthchecks.io, Better Stack or Cronitor, which alert when the pings stop, catching every server down, the database unreachable, or the alert loop wedged. [deployment.md](../deployment.md#alerts) recommends it beside the external uptime check.

### Outbound requests (webhook and heartbeat)

Both URLs come **only from configuration**, never from a request, and the client (`alerts.NewClient`) is careful anyway:
- **Validated at startup** (`config.loadAlerts`): an absolute URL with a host, **https** in production (http only outside it), no user name or password in it, no fragment, no space or line break, at most 2,048 characters. In production a host that is `localhost` or a loopback, private or link-local address is refused unless **`ALERT_ALLOW_PRIVATE_TARGETS=true`** (an internal relay). Messages never repeat the value: a Slack webhook *is* its URL.
- **Checked again at connection time** (`Dialer.Control`, in production unless allowed): the address actually dialled, after DNS, must be a public unicast address (`alerts.PublicAddress`: not loopback, private, link-local, site-local, multicast, unspecified, carrier-grade NAT, benchmarking, reserved, NAT64, 6to4, IPv4-compatible or -translated (`::127.0.0.1`), `2001::/32`, `192.88.99.0/24`, or a documentation range; an IPv4-mapped address is judged as its IPv4), so a name that resolves, or later resolves, to the server's own network (DNS rebinding) is refused with `ErrPrivateTarget`. **The remaining risk** if an operator allows private targets, or sets a URL at an attacker-controlled name in development, is an outbound request to wherever the configuration says: only an operator can set it.
- **No redirects followed** (`ErrUseLastResponse`: a 3xx is a failure), **no proxy from the environment**, TLS 1.2 at least, certificates verified, 5 s to connect, 10 s (webhook) or 5 s (heartbeat) in all, **at most 4 KiB of an answer read** and then ignored; only a 2xx is success.
- **Errors never hold the URL** (`withoutURL`), and the secret is never logged; the Configuration page and `server_instances.config` hold only whether each is set, the format, whether bodies are signed and whether private targets are allowed (`TestSummaryHoldsNoSecret`).

### The Alerts page and housekeeping

`GET /api/admin/alerts?state=open|resolved|all&before=alt_…&perPage=` (open by default: every open alert, critical first; the others newest first as a cursor page) and `GET /api/admin/alerts/{alert}`, recorded as `admin.alert.listed` and `admin.alert.viewed`. Each alert carries its signal's title, unit, page and thresholds, the rule's meaning, its `details` (the Events drill-down and an integrity check's sample public IDs: for the dashboard only), who acknowledged or silenced it, and how its opening was told. **`/api/admin/me`** gains `openAlerts` (the sidebar's count: not a recorded read) and `alertEmail`; the count is as of the page load.

| Action | Route | Tier | Event |
| --- | --- | --- | --- |
| **Acknowledge** an open alert (stops its reminders; the alert stays open and its webhook posts go on). **It needs no fresh code, by the plan**: an operator's session alone can stop an alert's reminder emails, which is why it only quiets reminders and hides nothing | `PATCH /api/admin/alerts/{alert} {acknowledged: true}` | housekeeping (`operator`, `admin-action:per-user`, no code, no reason) | `admin.alert.acknowledged` |
| **Resolve** an error group (a new occurrence opens it again) | `PATCH /api/admin/errors/{error} {resolved: true}` | housekeeping | `admin.error.resolved` |
| **Silence** an alert's signal for 1, 4 or 24 hours | `POST /api/admin/alerts/{alert}/silence {duration, reason}` | account-and-access `Action` (fresh code, reason) | `admin.alert.silenced` |

Silencing hides what may be a security alert, so it keeps `actions.md`'s step-up and reason. Housekeeping is registered with `Housekeeping`, which takes only the routes in `housekeepingRoutes` (the two above) and panics on any other (`TestAdminMutationsNeedARole`); the source test reads `routes.go` for it.

### Retention

Resolved alerts are kept **a year** (`make prune target=alerts`, on `resolved_at`; open ones never), the evidence of when something was detected and how fast it was answered; `alert.*` events are audit events (a year) ([compliance.md](../compliance.md#retention)).

### Tests

`internal/alerts`: an alert opens only after `For` and not before; doesn't flap across the 10 minutes; escalates in place instead of duplicating; resolves; a signal past its budget changes nothing; hourly rules once an hour; the notice for each opening (mail, held, digest, quiet, cooldown, a silence carried over); reminders every 4 hours unless acknowledged, never for a warning; only one of two runners evaluates and the other takes over when the first's session is terminated or released; the heartbeat only after an evaluation that worked; one email per admin at their setting and none for `none`; the webhook's body, signature, Slack shape, retries without the URL in the error, no redirect, the guard against non-public addresses, and the answer bound; no email or webhook holds the key, a link, an address, an IP or a name. `config`: the URL rules in production and development. `admin`: the pages, each read recorded once, bad parameters, viewers, the housekeeping and silence rules, `admin-action:per-user`.
