Web: `pages/admin/[key]/monitoring/index.tsx`, `security.tsx`, `limits.tsx`, `ips.tsx`, `ips/[ip].tsx`, `accounts.tsx`, `workspaces.tsx`, `usage.tsx`, `integrity.tsx`, `performance.tsx`, `errors.tsx`, `errors/[error].tsx`, `configuration.tsx`, `components/app/admin/monitoring.tsx` and `errors.tsx`. Plan: [monitoring](../../plans/features/admin/monitoring.md) (A4), shipped page by page: **part 1 is the groundwork, the Overview, Security and Rate limits; part 2 IP addresses (and one address), Accounts, Workspaces and Usage; part 3 Integrity, Performance, Errors (and one group) and Configuration**. The Data page (and `prune.completed`) comes after.

The app already records what an operator needs to spot trouble (every sign-in attempt and its result, every limit reached, request rates and latency, grouped errors). These pages turn each of those into a **signal**: a number with the levels at which it's a problem, a chart over time, and a link to the rows behind it. The dashboard runs inside the app it watches, so it can't say the app is down; an external uptime check does ([deployment.md](../deployment.md#logs-and-health-checks)).

## How every page works

- **One endpoint per page:** `GET /api/admin/monitoring/{page}?window=1h|24h|7d` (default `24h`), `admin.Monitoring.Show`, behind the admin key and an admin session like every admin route ([admin.md](admin.md#api)). `{page}` is one of the pages built (`monitor.PageNames()`: `overview`, `security`, `limits`, `ips`, `accounts`, `workspaces`, `usage`, `integrity`, `performance`, `errors`, `configuration`); any other is 404 "Page not found.", an unknown window 400 "Check the window.", any other parameter (or one given twice) 400. Viewers read every page: nothing here changes data.
- **One recorded read per page:** `admin.monitoring.viewed` (`admin`, `page`, `window`), actor only, written once the page was read, so a page's signals, charts and review lists are one read. A page that wasn't served (busy, too slow, an error) records nothing, since nothing was read. One address's page is its own read, `admin.ip.viewed` ([below](#one-address)), and so is one error group's, `admin.error.viewed` ([below](#one-group)).
- **Bounded:** a page is a set of aggregates, so it shares the Events charts' bound (`httpapi.Summaries`, [admin.md](admin.md#the-summary)): **one page or chart summary in flight per admin**, **two at once per server** (waiting at most 1 s for a slot), and a **5 s deadline** for the whole page. Within it, **each signal and each section has a budget of its own** (2 s, `Summaries.Section`; `monitor/sections.go`): one that isn't read in time is sent as not loaded (a signal with `unavailable: true`, a section's key in the answer's `unavailable` list, its data missing) and the rest of the page still answers, so a slow query, or one someone's own events slow down, hides its part and never the page (`TestAdminMonitoringSectionsFailAlone`). Past the slot it answers `503` "Monitoring is busy. Try again in a moment." (with `Retry-After: 1`); only when nothing at all could be read in time, `503` "This page took too long. Try a shorter window." `admin-read:per-user` still counts the request once. Every query is bounded by a window of 7 days at most (the review lists' takeover lookback reads one account's own sign-ins through its index), read through an index, and returns at most 20 rows per review list.
- **Computed when read** (decision 3), never stored. A signal too slow at real volume moves to the hourly rollup ([observability.md](observability.md#metrics-in-the-database)), not to a slower page.
- **SQL:** every query is Bun's builder in `internal/store/monitor_*.go`, values through `?` placeholders. Pages, windows, signals, limits and outcomes come from fixed Go tables; nothing from input becomes SQL text.
- **Emails and IPs only in review lists** (decision 7): the Security page's lists name the addresses and emails behind an attack, Rate limits' top addresses the addresses reaching the most limits, and the IP addresses page and one address's page the addresses events came from, admin-only and recorded; everywhere else is counts (the Accounts, Workspaces and Usage pages name accounts and workspaces by ID and name only, and one address's page counts the emails it tried that have no account, never naming them). An account is named by its `usr_` ID and name, never its email. No response holds a token, hash or internal ID (`decodeAdmin` walks every one in the tests).

### The response

```json
{
  "page": "security",
  "window": { "name": "24h", "from": "2026-10-31T14:30:00Z", "to": "2026-11-01T14:47:12Z", "bucketSeconds": 1800 },
  "signals": [
    { "name": "auth.failed_sign_ins", "label": "Failed sign-ins", "unit": "count", "value": 1204, "sample": 1204,
      "level": "critical", "warn": 100, "critical": 1000, "windowSeconds": 3600,
      "drill": { "name": "auth.login_attempted", "outcome": "failed", "window": "1h" } }
  ],
  "sections": { "…": "the page's own" },
  "unavailable": []
}
```

- **The window** is resolved by the server, like the Events page's (`monitor.ResolveWindow`; `TestMonitorWindowsMatchEvents` keeps them equal): it starts on its first bucket's boundary and runs to now. Buckets: 1 minute for `1h`, 30 minutes for `24h`, 3 hours for `7d`. Charts list every bucket, empty ones as zeros.
- **Signals keep their own windows** (an hour, a day, or "now"), whichever window the charts show: a signal says how things stand now, the charts how they got there. Each carries its `value` in its `unit` (`count`, `percent`, `ms`, `minutes`, `per_minute`), the `sample` it was counted from, its `level`, its thresholds and `minSample`, its window in seconds, and `drill`, the Events page's filter for its rows (`name` tokens, `outcome`, the `window` of the same length) when it has one.

## Signals (`internal/monitor`)

Each signal is defined once, in Go (decision 2): its name (stable: alerts and these docs use it), its page, label, unit and window, its **warn** and **critical** thresholds (0: no such level), an optional **minimum sample** (below it the level is `ok` whatever the value: a share of a handful means nothing), how it's measured (a store query), and its drill-down. **A value at or over a threshold is at that level**, the higher winning. Thresholds change only by a reviewed commit, and this table with them. **Anyone with an account can raise a level**: their own wrong passwords, codes and password checks, junk emails at sign-in, limits they reach on purpose. A level says something is happening, not that it's an attack on someone else, so the alerts that will read these ([alerts](../../plans/features/admin/alerts.md)) must allow for a level raised on purpose, to cry wolf or to hide something else in the noise. Alerts ([alerts](../../plans/features/admin/alerts.md)) will read the same definitions.

A signal's span is its window before now, its start floored to the window's bucket as the Events page floors the same window (an hour to the minute, a day to 30 minutes), so its drill-down covers the rows it counted (and any recorded since). **Only some drill-downs list exactly the rows counted** (`drillExact: true`): failed sign-ins, the unknown-account share (the attempts it's a share of), limit windows reached and sign-ups. The others list the events the number was counted from, which is more: stuffing and guessing (every attempt in the hour, not only the address's or email's), success after failures, takeovers (every such change), failed codes and password checks (every failure, not only the accounts' at 3+), the reset and shared limits (every `rate_limit.reached`), the sign-up limit, and the admin door (its failures' list holds the refusals of real credentials too, and the refusals' list the wrong passwords: the Events page has no filter for one result). The Events page has no filter that would make them exact, and none was added for it. `TestSignalsAreWellFormed` checks names are unique, every drill-down names only catalogue names or groups and a window the Events page takes, and warn is below critical.

## Overview

A grid of tiles, each an area with one or more signals: its worst level in words, its first signal as the number, the others listed under it with their levels, a sparkline over the page's window, and a link. Tiles: **Servers** (live, versions), **Requests**, **Server errors**, **Latency**, **Database** (round trip, minutes with pool waits), **Mail** (oldest waiting, failed), **Errors** (new, new panics, open), **Integrity** (critical and warning checks failing), **Failed sign-ins**, **Shared limits**, **Admin door** (refusals, failures), **Sign-ups** (sign-ups, active accounts).

- **Read order:** the Integrity tile's summaries are read after every other tile's signals (they run every check, the page's costliest reads), so a slow check uses up their own budgets and never the security tiles'. A partial summary says how many checks it read.
- **Links:** every tile links to its page (Configuration, Performance, Errors, Integrity, Security, Rate limits, Usage), Mail to the Mail page. **Alerts** has no tile until its page exists. With metric storage off on every live server (`metricsStore: "off"` in the answer, from the servers' summaries), Requests, Server errors and Latency say "Metric storage is off.": zero there isn't no traffic.
- **Sparklines:** connections in use (the pool gauge's average per server) per bucket; requests, 5xx share and p95 per bucket from the request minutes (over 7 days, the hours summed so far and the minutes after them, so nothing is counted twice: `requestRows`); failed sign-ins, shared limits reached, the admin door's failures and refusals, and sign-ups per bucket from events.

## Security

From `auth.login_attempted`, `auth.mfa.checked`, `auth.password_checked`, `auth.password_reset.*`, `auth.registration.requested`, `auth.registered`, `auth.logged_in`, `admin.login_attempted`, `admin.access_refused`, `admin.session.moved`, the takeover changes, `rate_limits` and `sessions`. Every review list groups by the hour from the window's start ("in an hour"), at most 20 rows:

| Section | Shows |
| --- | --- |
| Sign-in attempts | per bucket by result (signed in, right password and a code asked, wrong password, unknown account), and the share for unknown accounts |
| Credential stuffing | hour, address (linking to its sign-in attempts), distinct emails, attempts, how many signed in |
| Distributed guessing | hour, email (linking to its events), distinct addresses, failures |
| Success after failures | account, wrong passwords, when it signed in |
| Possible takeovers | one row per account (its newest such change, so one account can't fill the list): account, the new network, the sign-in, the change (linking to its event) |
| Second factor | accounts failing 3+ codes in an hour; recovery codes used; accounts left with 2 or fewer after using one (the payload's `recoveryCodesLeft`) |
| Password checks | accounts failing 3+ password checks in an hour |
| Password resets | asked for against sent per bucket (a gap is someone trying addresses), the addresses asking most, `password-reset:global` against its cap |
| Sign-ups | codes asked for and accounts made per bucket, the addresses making the most accounts, `register:global` against its cap |
| Admin door | counts per outcome (wrong password, unknown account, not an admin, admin without MFA, address not allowed, session moved), per bucket as failed sign-ins, refusals and moved sessions (three series: a chart stacks five at most, which `TestAdminMonitoringPages` checks for every chart), and the latest 20 with time, outcome and address (never the email typed), each linking to its event |
| Sessions | sign-ins per bucket, live app sessions, accounts at the 5-session cap |

**Indexes:** `events_name_created_idx (name, created_at DESC)` finds every name in its window; the takeover check looks only at the accounts that made a takeover change in the window (`events_name_created_idx`), starts from their sign-ins in the window (and the hour before), keeps those from a new network by comparing each with **the account's last 50 sign-ins** in the 30 days before it (one range of `events_logged_in_idx (user_id, created_at DESC) INCLUDE (ip) WHERE name = 'auth.logged_in'`, read from the index alone), and only then looks up the account's changes in the hour after each (`events_user_created_idx`). So an account recording thousands of its own changes doesn't slow it (`TestAdminMonitoringTakeoverFlood`), and nor does one signing in from a new network every time: each sign-in costs at most 50 index entries, where comparing with every earlier one was quadratic (6,720 such sign-ins took 6.2 s over a week; `TestAdminMonitoringTakeoverNetworks`). `sessions` holds live sessions only (the cleanup).

**What the takeover check can't see** (for [alerts](../../plans/features/admin/alerts.md) or a later plan): a change made **more than an hour after** the sign-in from the new network, and a takeover from a network the account **signed in from once before** in the 30 days (the attacker's first sign-in makes the network known, so a change after a second one isn't flagged). Tying each change to its own session's sign-in network would close both, but neither a session nor an event records the session it came from, so it needs a column of its own (`sessions.ip` or an event's session) and isn't built.

### One address

`GET /api/admin/ips/{ip}?window=1h|24h|7d` (`admin.IPAddresses.Show`): an IP address (an IPv4-mapped one as IPv4, never with a zone) or an IPv6 /64, its slash escaped (`2001:db8::%2F64`); anything else is 404 "Address not found." (`monitor.ParseAddress`). Bounded like a page (one per admin, two per server, 5 s) and recorded as **`admin.ip.viewed`** (`admin`, `address`, `window`; the address looked at is `address`, apart from the event's `ip` column, which is the admin's own): looking an address up is following someone. A refusal or a busy read records nothing. It answers, over the window and through `events_ip_created_idx` (`ip <<= ?`): the events and when the address was first and last seen in it, its events by name, the accounts seen from it (signed in, made there, failing to sign in; at most 20, by ID and name), **how many** different emails with no account it tried (never which: its events show them, a recorded read of their own), the limits it reached, and for a /64 its addresses (at most 20), and the live IP blocks holding it or part of its /64 (`blocks`: `network`, `expiresAt`; the page shows them in a warning with a link to the IP blocks page). An IPv6 address's answer names its /64 (`network`) to open. Everything recorded from the address counts here, admin reads included. An operator blocks it from here: **Block this address**, in the header right of the time range, opens the IP blocks page's dialog (`POST /api/admin/ip-blocks`, a reason and a fresh code: [admin.md](admin.md#ip-blocks)) with the address, or an IPv6 address's /64, filled in; viewers don't see it. The page reloads after (one more recorded read). `admin.ip.viewed`'s `address` is cut to its /24 or /48 at 30 days, like an event's `ip` ([compliance.md](../compliance.md#retention)).

## Workspaces

A workspace's rows have no time window of their own, so the page counts them only for **the workspaces with an event in the window** (`events_created_idx`), each counted through its tables' `workspace_id` indexes. A workspace grows only by writing, which records events, so one filling up is among them; one nobody touched in the window isn't counted.

| Section | Shows |
| --- | --- |
| Quota headroom | workspaces at 80%+ of a quota (projects 1,000; members and live invitations 100; live invitations 50) and their owners at 80%+ of 20 workspaces owned, each quota a `Meter` with its level in words |
| Rows per workspace | the 10 holding the most rows across **every table with a `workspace_id`** (`store.WorkspaceTables`: projects, members, invitations, events), a column per table and the total. Each table is counted up to 50,001 (`store.WorkspaceRowsCap`, the warning level) and shown as "Over 50,000" past it, so a workspace with millions of events costs no more than that per table |

**The workspace-tables registry** (decision 9): `store.WorkspaceTables` lists every table with a `workspace_id` column. `TestEveryWorkspaceTableIsMonitored` reads the columns from `information_schema` and fails when a table has one and isn't listed (or is listed and hasn't), and when a listed table has no index leading with `workspace_id` that isn't partial (`pg_index.indpred` null: a partial index serves only the rows it keeps); so a future table (tasks, files) is counted once it's added, without anyone remembering.

## Integrity

**Checks of things that should never be true** (plan A4's section 9). Each is a signal (`integrity.<check>`, at its level from one row: alerts will run the same definitions), one bounded query through an index that counts the rows breaking it (at most 1,000, then "1,000+") and names up to 10 by public ID (`store.CheckResult`). The two summaries count the checks failing at each level (the Overview's tile). A page's checks are run once, whichever asks first (the summaries, a check's signal or its list; `checkMemo`), and each is a part of its own, so one slow check shows as not loaded and never "OK". Rows with no time of their own are checked only for **the workspaces with an event in the last day**, as the Workspaces page counts them: the writes that break them record events. Those workspaces are read once per page (`IndexActiveWorkspaces`, from `events_created_idx`, which holds `workspace_id`; kept in the page's memo) and passed to each of the three workspace checks. **The summaries run the cheapest checks first** (a few rows, then an index window, then the workspace checks) and, when their budget runs out part way, count the checks they read and say so (`partial: true`, `sample` the checks read) rather than going missing (`TestAdminMonitoringOverviewIntegrityLast`).

## Errors

The grouped errors (`app_errors`) **last seen in the window**, newest occurrence first, at most 50 (`app_errors_last_seen_idx`; the table holds at most 1,000 groups between flushes and is pruned 30 days after a group was last seen): source, route, the scrubbed message, the count since first seen, first and last seen. Never a fingerprint or stack (one group's page has the stack). **New** marks a group first seen after the current release started: the newest `server.started`'s version, and the first start on it (`events_name_created_idx`, 7 days back); none started in 7 days, no release. The server sets each group's `new`, comparing the times (never their text, whose offsets may differ). **A browser's group** (`source: client`) is labelled **User-reported** and its text, like every group's, is shown as text, never a link: someone could write it. Occurrences per bucket by source come from `errors_total` (nothing with metric storage off). Read-only: resolving a group is an admin action (A6), marked in the pages.

### One group

`GET /api/admin/errors/{error}?window=1h|24h|7d` (`admin.Errors.Show`): an `err_` ID (`app_errors.public_id`, a column default); any other shape, or none, is 404 "Error not found.". Bounded like a page and recorded as **`admin.error.viewed`** (`admin`, `error`, `window`); a refusal or a busy read records nothing. It answers the group with its latest occurrence's **stack** (scrubbed: function names, files and lines), `lastRequestId` (to search the logs with: always ours), **`lastVersion` only in a release's shape** (`store.ReleaseShape`: a revision, `-dirty`, or `dev`; anything else is empty), the release now running, and its **route's occurrences** per bucket (`errors_total` counts by source and route, so every group on the route). "Versions seen" (the plan) isn't kept: a group keeps only its last version.

## Active accounts: `users.last_seen_at`

`users.last_seen_at` is when the account last used a session, to the hour. The session check (`store.FindSession`, behind `RequireSession` and the `/app/*` page gate) moves it **in the same statement** that refreshes the session's idle time, and only when it's null or over an hour old (`seenEvery`), so an active account costs one row write an hour and the check no extra round trip. It never records an event: it isn't something the account did, and an event an hour per account would fill the audit trail. It's null until the account's first signed-in request; an expired or idle session, or a suspended account's ([admin.md](admin.md#suspending-an-account): the same statement doesn't find its session), moves nothing. It never waits for the account's row (`FOR NO KEY UPDATE SKIP LOCKED`): changing the password or making a session locks the account and then its sessions, the other way round from the session check, so waiting could deadlock; a locked account's time just moves on its next request (`TestSessionCheckSkipsALockedAccount`). A partial index (`users_last_seen_idx`) serves counting the accounts seen since a time. `TestSessionCheckMovesLastSeenHourly` (`internal/store`) checks it, a suspended account's session included.

**Before migrations become append-only:** the column is edited into `002_create_users` while migrations are squashed, so every database rebuilt since has it from an account's first request. A database that gains it by a migration instead starts with it null for every existing account, which the inactive-accounts list reads as "never seen" (`coalesce(last_seen_at, created_at)`), so an old account active yesterday would look inactive. That migration needs a backfill first: each account's newest `sessions.last_seen_at` or `auth.logged_in` event (kept 90 days), whichever is later.
