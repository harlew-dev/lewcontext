# Design and components

Tailwind CSS v4 utilities in markup on top of Base UI behaviour, in a Catalyst-like style: restrained zinc, light and dark modes following the system setting, Inter, and Heroicons.

## Disclosure

`Disclosure` (`components/ui/disclosure.tsx`) is one collapsible item on Base UI's Collapsible: a full-width header (title, an optional `summary`, a chevron that turns), a panel whose height animates, collapsed unless `defaultOpen`, `bordered` for a card of its own. Lists of them are separated by `divide-y` on the wrapper. Used by the Alerts catalog's rules and the webhook dialog's example payloads. A raw `<details>` isn't used.

## Radio group

`RadioGroup` (`components/ui/radio-group.tsx`) is a choice of one among a few on Base UI's RadioGroup and Radio, styled like `Checkbox`: each option is its own label with an optional description, arrow keys move between them, and the group is named by its `label`. Use it for two to four options that should all be visible (the Subscribe dialog's level and format); a longer list is a `Listbox`.

## Incident thread

`IncidentThread` (`components/app/admin/incident-thread.tsx`) is the one discussion family for an alert's and an error group's page, built from `Button`, `Textarea`, `Badge`, `ListSkeleton`, `Notice` and the dialogs: cycle boundaries with the **Resolved incident** badge on the chosen comment, older cycles kept, comments as plain text (never a link), loading, empty, error-with-Retry and older-page states. The page file keeps its own health or occurrence content.

## Styling rules

- **Tailwind utilities only.** Use the default palette (zinc), default spacing, mobile-first breakpoints (`sm:`, `lg:`) and `dark:` variants. No per-component CSS files or custom colour tokens.
- **Complete class strings.** Map variants and colours to complete strings so Tailwind can detect them, e.g. `colors[color]`, never `` `bg-${color}-500` ``.
- **`className` is for placement and spacing.** Components merge it with `cx(className, own…)`, so don't pass utilities that compete with a component's own classes.
- **Icons are Heroicons** (`@heroicons/react/16/solid` or `20/solid`). They carry `data-slot="icon"`, which the component styles size and colour.
- **Respect reduced motion.** `MotionConfig reducedMotion="user"` covers motion, and plain transitions use `motion-reduce:` variants.
- **Hover and focus backgrounds slide.** In a group of items (sidebar sections, tabs, menu items, listbox options) the hovered or focused item's background is one shared `Highlight` (`components/ui/highlight.tsx`) that slides from item to item ([Sliding highlight](#sliding-highlight)).
- **Pages fade in.** `PageTransition` (`components/layout/page-transition.tsx`) fades a new page's content in and lifts it 6px over 200 ms with CSS `@starting-style` (Tailwind's `starting:`), so it needs no JavaScript and leaves no transform behind. The app layout keys it with `usePageKey()`: the pathname (a new search or page number isn't a new page), or for tabs, the tab group's path, and `AuthLayout` wraps each sign-in page in it. Browsers without `@starting-style`, and reduced motion, show the page at once.
- **Tabs are one page.** Tabs that are pages of their own (workspace settings' General and Members) live under a layout route that renders the heading and tabs and exports `handle: TransitionHandle = { tabGroup: true }`. The tabs stay mounted, so the current tab's underline slides (`layoutId`, as in the sidebar); the app layout doesn't fade the page in again; and the layout wraps the content below in `PageTransition from="left" | "right"`, keyed by pathname, so it slides 12px in from the side of the tab chosen (enter only; the old tab goes at once). Nothing slides on arrival or when only the workspace changes.

## Base UI underneath

What Base UI is, how it's set up and its known issues are in [base-ui.md](base-ui.md). This section is how we style it.

Base UI provides behaviour (focus, keyboard, overlays) for Button, Input, Checkbox, Select (→ `Listbox`), Combobox, Dialog (→ `Dialog`, the mobile sidebar), Menu (→ `Dropdown`), Tooltip and Toast.

- Each part is ours to style with `className`, and its state is in data attributes the classes target: `data-highlighted`, `data-selected`, `data-checked`, `data-disabled`, `data-popup-open`, `data-starting-style`, `data-ending-style`. Plain links and buttons get `data-hover`, `data-active` and `data-focus` from `useInteractive` (`lib/interactive.ts`), via `Link`, `Clickable` and `Button`. Our own `data-invalid` and `data-blurred` mark an invalid or blurred input.
- Don't use `style` for what a class can do. Popups size and place themselves with Base UI's CSS variables (`--anchor-width`, `--available-height`, `--transform-origin`).
- **Overlays animate in and out in CSS.** Base UI keeps an overlay mounted until its transitions end, marking the start with `data-starting-style` and the end with `data-ending-style`. `Dialog` and the mobile sidebar transition their backdrop and panel on those; menus, listboxes and tooltips use `popoverPanel` (`lib/transitions.ts`), a fade, on the panel itself (an ancestor with opacity below 1 would turn off `backdrop-blur`). Plain `transition` classes with `motion-reduce:transition-none`, so reduced motion is respected. A dialog animates open under `make dev` as in production, and one that mounts already open (keyed per opening with `useOpenCount`, which Base UI gives no `data-starting-style`) animates from CSS `@starting-style` (Tailwind's `starting:`; browsers without it open without the animation).
- **Open overlays stop the page scrolling**, with Base UI's own lock (a dialog, a menu, a select): it hides the page scrollbar without shifting the layout and keeps the scroll position.
- **A dialog over another dialog dims it.** Base UI nests them natively (Escape closes only the top one); each layer renders its own backdrop (`forceRender`), so the dim compounds, and the panel classes take `data-nested:shadow-xl` with a harder ring and `data-nested-dialog-open:scale-[0.98]` to recede the parent (`components/ui/dialog.tsx`).
- **Overlays give focus back to whatever opened them.** Menus and selects use Base UI's. A `Dialog` remembers the element focused as it opened and refocuses it as it goes (`ReturnFocus`, `lib/return-focus.tsx`, with `finalFocus={false}`), since a dialog opened from a menu item has no opener of its own. A `DropdownItem` closes its menu first and runs its `onClick` once focus is back on the trigger, so a dialog opened from a menu returns focus to the menu's button. `keepOpen` items ("Show more", "Retry") act inside the open menu.
- **`Listbox` opens over its button** with the selected option on top of it (the positioner's `alignItemWithTrigger`, which turns itself off for touch), with a panel at least as wide as the button plus the check mark's gutter.
- Classes target the attributes: `data-hover:bg-zinc-950/5 data-focus:outline-2 data-disabled:opacity-50`.

## Charts

`components/ui/chart.tsx` is the only file that imports Recharts ([README.md](README.md#dependencies)); pages pass rows and series and never style Recharts themselves. Monitoring's `Sparkline` and `Meter` live there too.

- **Colours by series, in a fixed order, never cycled:** sky, orange, emerald, violet, pink, as complete `text-*` classes the marks fill with `currentColor` (`600` shades and `pink-500`; violet steps to `500` on dark). Checked with the dataviz skill's validator against white and zinc-900 with **every pair** compared, since any two segments of a stack can touch: full-colour ΔE ≥ 16.8 and every mark ≥ 3:1; colour-blind ΔE ≥ 7.3, the band that needs a second cue, which the gaps, legend, tooltip and table give. Amber or yellow beside orange, or blue beside violet, fail that check. A sixth series is folded into "Other" by the page. Red, amber and green as _levels_ belong to monitoring (`LevelBadge`, a `Meter` at a level) and always come with a word, never colour alone; no series uses them.
- **Quiet marks:** columns at most 24px wide, a 4px rounded end on the top segment only, square at the baseline, a 2px gap in the card's colour between stacked segments; hairline zinc gridlines, no axis lines; ticks and labels in text colours, never the series colour.
- **Accessible:** the SVG is `aria-hidden`; the `figure` carries the `summary` sentence and a `sr-only` table with every value. The tooltip shows the value first, then the series, keyed by a short line of its colour. Animation is off under reduced motion.
- **Tests** check the table's numbers: jsdom has no layout, so the SVG doesn't render there.
- **`Sparkline`** is one series, so it has no legend (its tile names it): sky, a 2px line over a fading fill, a tooltip with the value first, and its numbers as a `sr-only` table (the hidden tables sit in a `sr-only` box: a table is never narrower than its one-line text, so on its own it would widen a phone's page). **`Meter`** is plain HTML: a rounded bar in sky, amber (warning) or red (critical), beside the level's word on the page.
- **Show as table** (`BarChart tableToggle`, every Monitoring chart) turns the screen-reader table into a visible one, for anyone who'd rather read numbers or can't use the pointer-only tooltip.
- **`BarList`** is plain HTML, not Recharts: an `<ol>` of links whose bars are `bg-sky-600/15` (`dark:bg-sky-500/20`), as wide as their share. A list of links reads as it is, so it has no hidden table.

## Descriptions

A title doesn't need a description under it. Add one only when it tells the reader something they need that the title and the content beside it don't already make clear; never restate the title ("Password" → "Change your account password").

- **Leave it out** for settings sections whose fields, buttons and lock tooltips explain themselves: General, Workspace ID, Profile, Password, Two-factor authentication, Sign-in sessions.
- **Keep it** where it carries consequences or rules the reader can't infer: every `DangerAction` row (the danger zone itself carries no description), confirmation dialogs, and empty states.
- **A description sits right under its title**, read as a subheading, never spaced as the next section. On the sign-in and status pages, whose forms are `gap-8` grids, the page's `Heading` and its `Text` go in one `HeadingGroup` (8px apart); `SettingsSection` (4px) and `DialogTitle`/`DialogDescription` (8px) already do this, and a page heading's line of context takes `mt-1` or `mt-2`.
- A reason something can't be changed goes in its `Field locked`, not in a description ([Locked fields](#locked-fields)).

## Locked fields

A value someone can see but not edit in that field (a workspace ID, the workspace name for a member, or email changed through a separate security flow) is a `Field locked`: `true`, or better the reason ("Only owners can rename this"; `true` says "Can’t be changed").

A value that can be edited but whose change needs more proof than the form's Save (the account email in settings) is a `Field guarded="Protected"`: the `Input` stays editable and ends with a shield (`ShieldCheckIcon`) in the lock's place, whose tooltip (the text given, also the icon's accessible name and the control's description) opens on hover and focus only, never on typing, pasting or dropping, since nothing is refused. The page's Save then asks for the proof, in a dialog.

- **The `Input` turns read-only** (never `disabled`: it stays focusable, selectable and copyable) and **ends with a lock**: the last of its `InputGroup`'s `InputActions`, after an eye or Copy button, or in a group of its own when the `Input` has none. A locked `InputGroup` needs `InputActions` for the lock to go in, even empty.
- **The reason is the lock's tooltip** (on hover and keyboard focus, its accessible name) **and the input's description**, so a screen reader reads it with the field.
- **Trying to edit it answers.** A character, Backspace or Delete, Ctrl/⌘+V or X, a paste or a drop opens the lock's tooltip (`Tooltip open`) for 3 seconds after the last try. Escape or leaving the input closes it; Tab, arrows and Ctrl/⌘+C don't count.

## Secrets and sensitive values

API-key creation moves the same dialog to a one-time secret step: a zinc callout with Reveal's decoy placeholder, a ghost Copy icon at its top right with Copy/CopyFailure (Copy works masked), the request in an "Example request" Disclosure, an API Documentation link that opens in a new tab with an external icon, and Done. The real credential is absent from masked DOM. With MFA enabled, Add API Key (or Save changes when broadening) opens a nested Confirm your identity dialog over the filled form. Only that dialog contains authenticator/recovery input; Cancel/Escape clears the code and returns focus to the parent submit button, preserving the form. The authenticated creation/update still happens in one request. Password proof without MFA stays in the key form. Closing early uses `ConfirmationDialog` to warn that the secret will be lost, without revoking the committed key. Row actions are three-dot menus: Edit and danger Revoke, with no edit/menu for ended keys and no Edit for other members' personal keys. Shared form/list components live in `components/app/api-keys/`; permissions reuse the grouped, searchable Combobox without importing admin modules.

Two kinds of value stay unreadable until asked for, in case the screen is shared or recorded, each behind an eye or a reveal button:

- **Secrets** let someone into the account: a QR code, a setup key, recovery codes. They stay out of the page until shown: `Reveal` renders only a decoy placeholder, and a masked field holds bullets, never the value. Never blur a secret; a screenshot of a blur can be undone.
- **Sensitive** values are personal but grant nothing alone: your email address in account settings. They're in the page, drawn blurred with `Input blurred`, so the field still reads as a normal field (not a password) and screen readers read it. Pass `onReveal` so a click on the field reveals it, and add an eye `InputButton` (tooltip "Reveal" / "Hide", `aria-pressed`) first in its `InputActions` for the keyboard. The blur is drawn over the input, not as a text shadow, which the input would clip to its line.

## Copying

Every Copy button is a `CopyButton` (`components/ui/copy-button.tsx`) driven by `useCopy`: the workspace ID in workspace settings, the setup key and the recovery codes in two-factor setup (account settings and the admin sign-in). Don't write a clipboard call or a "Copied" message by hand.

```tsx
const copy = useCopy(value, { onCopied });
<CopyButton copy={copy} label="Copy Workspace ID" />                 // in InputActions
<CopyFailure copy={copy}>Couldn’t copy. Select the ID and copy it instead.</CopyFailure>
```

- **"Copied" is a tooltip on the button, never text on the page.** After a click it shows for 3 seconds and hides itself (the icon turns to a check meanwhile); hovering or focusing the icon variant shows "Copy" as usual. It's `Tooltip open` held for that time, as a locked field's lock does.
- **Screen readers hear "Copied" once**, from a `sr-only` `role="status"` region beside the button, emptied before each copy so a second one is announced again. The tooltip's own text is `aria-hidden`, so it isn't read a second time as the button's description.
- **Where the clipboard isn't available** (an insecure origin, a refused permission), `CopyFailure` shows what to do instead under the field or button, as an alert, and keeps it there until the next try: an instruction mustn't vanish before it's read.
- `onCopied` runs after each copy that worked (the recovery codes count as saved), never after the component has unmounted, however late the clipboard answers.

## Confirmations

Every "are you sure?" is a `ConfirmationDialog` (`components/ui/confirmation-dialog.tsx`): removing a member, leaving or deleting a workspace, deleting a project or the account. Don't build one from `Dialog` by hand.

```tsx
<ConfirmationDialog
  open={open}
  onClose={() => setOpen(false)}
  title={`Delete ${project.name}?`}
  description="This permanently deletes the project. It can’t be undone."
  confirm="Delete project" // the button says what it does
  variant="danger" // red confirm button; "default" is dark/zinc
  disabled={typed !== name} // e.g. type-to-confirm
  onConfirm={() => api.projects(ws).destroy(project.id)}
  onConfirmed={() => toast.success("Project deleted.")}
  onError={showOnField} // optional: an ApiError with a field, shown under it
>
  {/* optional fields: type-to-confirm, password */}
</ConfirmationDialog>
```

- **Also for a dialog with one action and no fields to fill**, which says what will happen and asks to go ahead: "Didn’t receive the email?" (Cancel · Resend code, `EmailCodeStep`; the sign-up's blocked-address text is its `body`).
- `onConfirm` runs through `useAction`: the button shows `loading`, a double click confirms once, and Cancel, Escape and the backdrop do nothing until it settles. The fields are disabled meanwhile.
- A failure keeps the dialog open with the error (`ErrorNotice`) and the typed fields. Success closes it, then calls `onConfirmed`.
- Key the dialog per opening with `useOpenCount(open)` (`lib/use-open-count.ts`): `key={opened}`, so each opening starts empty, without the last opening's values or error. A dialog keyed by its target instead (`"new"`, a project ID) keeps whatever was typed last time; that was the "forms don't reset after submit" bug.
- A dialog whose consequences need to stand out puts them in a `<Notice variant="warning">` at the top of its fields, with a short `description` saying what to do (Delete workspace). Type-to-confirm labels show the name as `“<Code>Acme</Code>”`.
- Labels name what they act on: "Delete project", "Delete workspace", "Delete account", never a bare "Delete".
- Destructive actions sit in a danger zone at the bottom of settings (`SettingsSection variant="danger"` with `DangerAction` rows), or as a `DropdownItem variant="danger"` in a ⋯ menu (`ProjectActions`).

## Sliding highlight

`components/ui/highlight.tsx` draws one background per group that slides to the hovered or focused item (a `motion` `layoutId` with a short spring), as the sidebar does.

| Where                                                                                                                                                   | Group                                                                                                                                                        | Which item has it                                                                                                                                                                                                                  | Colour                                                              |
| ------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| `Sidebar` (all its `SidebarSection`s, so the highlight and the current-page indicator also slide between sections), `NavbarSection` (tabs, the top bar) | `useHighlightGroup()` in its own `LayoutGroup`; cleared when the pointer leaves the sidebar or section                                                       | the item the mouse is over (`useHighlight().activate()` on `pointerenter`)                                                                                                                                                         | `bg-zinc-950/5` / `dark:bg-white/5`                                 |
| `DropdownMenu`                                                                                                                                          | the same; cleared when focus leaves the items (the mouse leaving the menu hands focus back to its `selected` item, or else to the menu, as Headless UI does) | the item Base UI highlights (`data-highlighted`, on hover and arrows; the highlight stays while the pointer crosses a divider and goes when the pointer or focus leaves the menu; the menu opens with its `selected` item focused) | `bg-zinc-950/5` / `dark:bg-white/10`; a default item's icon darkens |
| `Listbox`                                                                                                                                               | none needed: its own `LayoutGroup`                                                                                                                           | the option Base UI marks `data-highlighted` (the option's `render` draws it from `state.highlighted`)                                                                                                                              | `bg-zinc-950/5` / `dark:bg-white/10`                                |

- **The selected option stays blue.** In a `Listbox` the chosen option has a static `bg-blue-500` background with white text and its check mark, above the grey highlight (`-z-5` over `-z-10`), so hovering it changes nothing and the grey slides beneath it.
- **Nothing slides while a menu or listbox opens.** Base UI positions the popup before its first paint, so the first highlighted item appears in place and the highlight slides only from there.

- **Items outside a group** (a `SidebarItem` or `NavbarItem` not in a section) keep a plain `data-hover:` background.
- **Under the text while it slides.** In menus and listboxes the highlight is `-z-10` inside the panel's `isolate` stacking context, so it passes beneath every item's text. Don't make an item `isolate`: the highlight would then paint over the items before it mid-slide. In the sidebar and tabs it comes before the item's `relative` link in the DOM instead.
- **Forced colours** hide it (`forced-colors:hidden`); the items' own `forced-colors:` backgrounds apply.
- **Reduced motion** (`MotionConfig`) moves it without sliding.
- **Fixed panes need a scroll root.** Motion measures `layoutId` elements in page coordinates (viewport position plus the window's scroll), which is wrong inside a `position: fixed` pane: the highlight or current-page indicator would slide in from a scroll's distance away after the page scrolls or a navigation resets the scroll. The desktop sidebar's content sits in `SidebarScrollRoot` (`sidebar-layout.tsx`), a fixed `motion.div` (the sidebar's own width, never the viewport's) with `layoutScroll` that never animates, so Motion measures it in viewport coordinates. A new fixed or sticky pane holding sliding items needs the same. It is its own element because the sidebar wrapper animates `translate` in CSS, which Motion's `layout` would fight. The mobile drawer needs none: its scroll is locked while it's open.

## Toasts

`toast.success(message)` and `toast.error(message)` (`components/ui/toast.tsx`) show a short-lived message in a stack at the bottom right (across the bottom on phones): the newest in front, the older ones peeking out behind it, fanning out while the stack is hovered or focused.

- **Successes** of any action are toasts: "Workspace renamed.", "Project created.", "All other sessions have been signed out."
- **Errors** stay inline when the action is a form (`<ErrorNotice error={action.error}>` beside its fields, see [api.md](api.md#changing-data)), and load failures keep their `Notice` with Retry. An action that is only a button, with no fields (sign out, sign out other sessions), reports its error as `toast.error`.
- A toast belongs to the `Toaster` that was mounted last. A toast shown just before navigating to a page outside the app layout (onboarding, login) is lost with the layout, and React Router commits a redirect after `navigate()` resolves. Say it on the next page instead, through navigation state: login's "Your account has been deleted.", onboarding's "<workspace> deleted." and "You left <workspace>.". Arriving in the app layout from outside it works the same way: `arrivalState` carries `joinedWorkspace` or `createdWorkspace`, and the layout's `ArrivalToast` shows "You joined Acme." or "Acme created." (creating from the switcher uses the same form, so it goes this way too).
- **Every finished action says so.** Creating, renaming, leaving and deleting a workspace; creating, editing and deleting a project; inviting, changing a role, removing a member, revoking an invitation; profile, password and other sessions. Signing out and deleting the account end on login, which is its own confirmation (login says the account was deleted).
- A toast hides after 5 seconds, paused while it's hovered or focused. Pass `{ duration }` in milliseconds to change that, or `Infinity` to keep it until dismissed.
- It's Base UI's `Toast` (timer, stacking, with a module-level manager that `toast` calls): a zinc panel with the `Notice` variant's icon and role (`messageVariants` in `feedback.tsx`, so the two stay alike) and our `DismissButton`, sliding in and fading out on `data-starting-style` and `data-ending-style`. The stack shows up to five. Swipe to dismiss is off.
- `<Toaster />` is mounted by `pages/app/layout.tsx` and onboarding only, so signing out unmounts it and any open toasts. Calling `toast` where no `Toaster` is mounted shows nothing (in tests, render a `<Toaster />`).

## Sidebar layout

`SidebarLayout` (`components/layout/sidebar-layout.tsx`) is the signed-in chrome; `ApplicationLayout` fills it with the workspace menu, navigation and account menu.

- **Where the menus live.** The workspace menu is in the sidebar's header and, duplicated, at the right of the top bar, so switching workspace is one tap on a phone and with the sidebar hidden. The account menu is only in the sidebar's footer, on phones too (open the slide-over sidebar). "Getting started" is always in the sidebar, so the account menu doesn't repeat it.

- **Desktop:** the sidebar is docked on the left. `<SidebarToggle />`, beside the workspace menu, hides it: the sidebar slides out, the content widens, and a top bar opens with the workspace menu. All three move together over 300 ms.
- **One toggle that glides.** The toggle is a single button that never leaves: hiding the sidebar glides it from beside the workspace menu into the top bar's corner, and showing glides it back. It stays visible (with `visible`) while the sidebar is invisible, its label switches between "Hide sidebar" and "Show sidebar", and focus stays on it. Its glide distance (`desktopToggleClasses`) follows the sidebar header's padding and the button's size, so change them together.
- **Remembered on this device.** `useDockedSidebar` (`lib/use-docked-sidebar.ts`) stores `lewcontext:sidebar=hidden` in `localStorage` (docked is the default and isn't stored). It reads the value while rendering, so the first paint is already right: the app layout renders only in the browser (never prerendered), and no effect flips it after mount, which would flash the sidebar and play its slide. Without storage (blocked, private windows) the sidebar starts docked and the toggle still works.
- **Hidden means out of reach.** The hidden sidebar turns `invisible` (out of the tab order and the accessibility tree) once it has slid out, and visible at once when it returns; the top bar does the same while the sidebar is docked.
- **Mobile:** a top bar with the menu button on the left and the workspace menu on the right (avatar, truncated name, chevron); the account menu is at the bottom of the slide-over sidebar. Opening another page closes the slide-over, also from a menu in it (`SidebarLayout` watches the pathname). The slide-over sidebar's close button sits where the desktop toggle does, beside the workspace menu (`SidebarToggleContext` tells `SidebarToggle` which sidebar it's in).
- **Matching heights.** `SidebarToggle` is an icon-only `SidebarItem`, so it's exactly as tall as the workspace menu (36px, 44px on phones). Icon-only items keep their full-size icon: the trailing-chevron sizing skips an item whose icon is its only content (`*:not-nth-2:last:`), in both `SidebarItem` and `NavbarItem`.

## Where you are

The sidebar has only Overview and Projects (plus Getting started); the settings pages live in menus. So that you can still see where you are:

- **A page in the sidebar** is its `SidebarItem current`: the indicator bar slides to it.
- **A page in a menu** selects the menu's button (`DropdownButton as={SidebarItem | NavbarItem} selected`, a grey background). Workspace settings (General and Members) select the workspace menu, in the sidebar header and in the top bar (phones, or the desktop sidebar hidden); account settings select the account menu in the sidebar footer. Inside the menu the page's item is `DropdownItem selected aria-current="page"`, a default focus: the menu opens with it focused (and so highlighted; Enter opens it, the arrow keys move on from it), hovering another item takes focus and the highlight away, and the mouse leaving the menu returns them to it.
- **The workspace you're in** keeps its check in the switcher (and `aria-current`).
- Don't add sidebar items for settings pages.
