# Forms and actions

Where buttons go, which style they take, and in what order, for forms and for one-off actions. **Follow this for every button you add.** If a place doesn't match one of these patterns, ask rather than inventing a new layout.

The short version: **actions sit at the bottom right of what they act on**, the primary action is the rightmost one, and only the sign-in pages use full-width buttons.

### Back on the sign-in pages

Moving to another page is the browser's own Back, or a link on the page: there is no Back button under the logo for that. A step on the same page that the browser can't reach keeps one: `BackButton` (`components/layout/auth-layout.tsx`), a `plain` button with a left arrow. It sits in the form's action row on the left of the submit button, which takes the rest of the width (`sm:flex-1`); on phones both are full width with Back first, one per row. The one step back with no submit button (forgot password's "Check your email") keeps Back under the logo.

| Page                                                | Back goes to                                                                  |
| --------------------------------------------------- | ----------------------------------------------------------------------------- |
| Login's and the admin door's code step (`CodeStep`) | the password step, the email kept (it was "Sign in as someone else")          |
| Forgot password's "Check your email"                | the form, the email kept, to try again (it was Try again and Back to sign in) |
| The admin door's MFA setup                          | the password step (until MFA is on; then the codes lead on to Users)          |

Links to somewhere else (Sign up, Sign in from the code page, Forgot password?, register's "Already have an account? Sign in") stay text links. Pages with nowhere to go back to have no Back: the admin door's password step, the invitation and block-link pages (they start a flow from an email), onboarding, verify email (its way out is Sign out), and a sign-up that has ended (its one button is Back to sign up).

Everything signed in and outside a dialog follows the settings rows: right-aligned, never left-aligned or full-width. The sign-in pages are the only exception, because their single action is the whole page.

## Order and style

- **Primary action last (rightmost)**, solid (`<Button>`, `dark/zinc`). Secondary actions to its left: `plain` for Cancel and Back, `outline` for an alternative that does something (Try again).
- **At most one solid button per group.** A one-off action that isn't the main thing on the page is `outline` (Change password, Sign out other sessions).
- **Red (`color="red"`) only for destructive actions**, and only in a danger zone or as a `ConfirmationDialog`'s confirm button (`variant="danger"`). In a ⋯ menu use `DropdownItem variant="danger"` instead. See [design.md](design.md#confirmations). **Sign out is not destructive,** so in the account menus (the app layout's, onboarding's and the admin dashboard's) it's a default `DropdownItem`, after a divider; never red.
- **Labels say what happens**, with a verb: "Save", "Create project", "Delete workspace", "Sign out other sessions". Never "OK", "Submit" or a bare "Delete".
- **Cancel** never has a destructive or primary style. It's disabled while the action runs, as dialogs already do.

## Behaviour (same everywhere)

**API keys:** Add API Key sits in the list's header action row; its Dialog has Name, explicit Expiry (Never included), Project access, grouped Permissions, and a workspace selector for personal creation. Selected projects search through the Combobox input and load more API results as its popup scrolls. Without MFA, fresh password proof stays in the form. With MFA, clicking Add API Key (or Save changes when broadening) opens a nested Confirm your identity Dialog: the authenticator/recovery field, Cancel · Add API Key / Save changes. Cancel/Escape preserves the parent form, clears the code and returns focus to its submit button. A failed proof stays in the nested modal; successful authenticated creation/update closes it. No key is issued just by opening it. Cancel · Add API Key / Save changes, primary last. Success switches creation to the one-time masked secret/copy step with Done; early close warns via ConfirmationDialog. Edit/Revoke sit only in the right-aligned row menu; Revoke is danger and opens Cancel · Revoke API key, explaining immediate integration failure. Rotation explains strict capacity/downtime before instructions.

The account email field in settings is editable (blurred until revealed or typed in) and `guarded`: it ends with a shield whose tooltip says **Protected**, and there is no separate button and no explanatory description. Its description appears only for a request already sent: **You have an email change request. Continue**, the link resuming that request at its code (after the **Verify email** one when the address is also unverified). Save handles both fields: a changed name is saved at once (so it survives a closed dialog), and a changed email then opens the shared dialog already at confirming account access; Save stays disabled while neither differs, and an address that differs only in case or spaces is no change. The dialog's destination and account-access steps are Cancel · Continue / Send code / **Change email address**, with no Back: Cancel closes the dialog, and a typo is fixed by reopening it. Saving always opens it the same way, whether or not an earlier request exists: it never mentions that one, and confirming account access replaces it. Opened without a typed address (the description's Continue, onboarding's menu, the gate), it resumes a waiting request at its code, or asks for the new address if none waits. Code entry is Close · Cancel change · **Change email address**: Close only dismisses, Cancel change deletes the request and ends on a **Your change has been cancelled** screen with only a **Close** button at the bottom right. The dialog has no description under its title on any step. Resend returns to fresh account proof. Completing keeps the dialog open on a success screen with one **Done** button (Escape and the backdrop do the same); the page's follow-up (the gate's return through `next`) runs only once it is dismissed. Onboarding's account menu and the verification gate open the same dialog at its first step, with the destination field. Primary actions remain last in `DialogActions`, and the active mutation prevents dismissal and duplicates.

- **Pending:** run the action through `useAction` and pass `loading={action.loading}` to its button, so a double click submits once ([api.md](api.md#changing-data)). Disable the form's fields while it runs (`disabled={action.loading}`).
- **Nothing to save:** a settings Save is `disabled` until the value differs from what's saved and would be accepted (`disabled={clean === null || clean === saved}`).
- **Say why it's disabled:** a button disabled by the form's state passes `disabledReason`, in one of two wordings: "No changes made" (nothing differs from what's saved) or "Fill in required fields" (something needed is empty or invalid), e.g. `disabledReason={clean === null ? "Fill in required fields" : "No changes made"}`. Not for `loading`, which explains itself.
- **Submit buttons** are `type="submit"` inside a `<form onSubmit>`, so Enter submits. Other buttons in a form are plain buttons (`Button` defaults to `type="button"`).
- **Errors:** a form's failure is an `ErrorNotice`; a one-off action with no fields reports its failure as `toast.error`. Successes are toasts ([design.md](design.md#toasts)).

## Examples

```tsx
// Settings form: fields, then Save at the bottom right, then the error.
<form onSubmit={submit} className="space-y-4">
  <WorkspaceNameField label="Name" value={name} onChange={setName} disabled={rename.loading} />
  <div className="flex justify-end">
    <Button type="submit" loading={rename.loading} disabled={clean === null || clean === workspace.name}>
      Save
    </Button>
  </div>
  <ErrorNotice error={rename.error} />
</form>

// One-off action in a settings section.
<div className="flex justify-end">
  <Button outline loading={revoke.loading} onClick={revokeOthers}>
    Sign out other sessions
  </Button>
</div>

// Dialog: secondary first, primary last.
<DialogActions>
  <Button plain onClick={close} disabled={save.loading}>Cancel</Button>
  <Button type="submit" loading={save.loading}>Save changes</Button>
</DialogActions>

// Sign-in page: one full-width primary.
<Button type="submit" className="w-full" loading={loading}>Sign in</Button>
```

## Checking your change

Look at the page at phone width and at desktop width (`make dev`) before calling a UI change done. Every action should be at the bottom right of what it acts on, or full width on a sign-in page, with the primary rightmost (or on top when stacked).
