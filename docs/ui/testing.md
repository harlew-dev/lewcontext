# UI tests

## Running

```sh
make test                  # includes Vitest (cd apps/web && npm test)
make check                 # TypeScript, ESLint (zero warnings), Prettier (and the Go checks)
make build                 # web build (react-router build), embedded into bin/api
make test-e2e              # Playwright: builds and starts its own server on :3100
make test-e2e E2E_PORT=auto  # the same on a free port, beside another run
cd apps/web && npm audit
```

## Vitest + React Testing Library

- Files sit next to the code as `*.test.ts(x)` and run in jsdom (`vitest.config.ts`, setup in `tests/setup.ts`). Vitest runs from `apps/web`. It has its own config, without the React Router Vite plugin.
- **Shared setup:** `tests/setup.ts` runs `cleanup()` and `vi.unstubAllGlobals()` after every test, so test files don't repeat them.
- **Faking the API:** `stubApi` from `src/test/api.ts` answers `fetch` from a table of `"METHOD url"` keys (the exact URL, then the path without its query, then `"*"`) and records what was sent:

  ```ts
  const api = stubApi({
    "POST /api/auth/password/verify": { status: 204 },
    "PATCH /api/auth/password": [{ status: 422, body: { error, field } }, { body: session }],
    "*": { body: {} },
  });
  api.sent("PATCH"); // [{ method, url, body, csrf }]
  ```

  A list of replies is used in order and its last one repeats; anything unmatched gets a 404 naming the missing stub. A reply can hold its response until a `gate()` is released (to check pending states) or fail as if the network were down (`network: true`). `testSession(overrides)` from `src/test/session.ts` is a signed-in session to pass to `SessionProvider`. Only `lib/api/http.test.ts` (the transport, with raw `Response`s) and `lib/use-resource-pages.test.tsx` (an outage that changes mid-test) stub `fetch` themselves.
- **Routing in tests:** components that render links need a router: `render(ui, { wrapper: MemoryRouter })`. Hooks that navigate are tested by mocking `useNavigate`/`useLocation` with `vi.mock("react-router", async (importOriginal) => ({ ...(await importOriginal()), useNavigate: () => navigate }))`.
- **Query by role and accessible name** (`getByRole("link", { name: "Page 2" })`), and assert on behaviour: links, `aria-current`, `aria-sort`, `aria-busy`, disabled state, callbacks. Don't write tests that only mirror styling.
- **Pure helpers get table-style tests:** `lib/pagination.test.ts`, `lib/ids.test.ts` (`parsePublicId`). `pages/auth/invitations.test.tsx` renders the invitation page through `createRoutesStub` (its loader gives the session): signed out (the callout, links carrying `next`, the token only in the check's body), names rendered as text, dead and malformed links (no request), Join only when asked or at once with our navigation state, the wrong account switching, and login and register showing the invitation, prefilling its email, keeping it when switching, and register returning to the link instead of onboarding. `members.test.tsx` also covers Invite (only your assignable roles, never owner; a refused email on its field; a refusal for the address, `invitation:per-email`, shown in the dialog with the email kept; the toast and the refreshed list) and the pending list (Sending…, Sent, Expired, revoking only roles you may give). `lib/swr.test.tsx` checks that a 4xx read isn't retried (a 429 is fetched once, Retry asks again) while a 500 is retried twice, and that a refused mutation shows the API's message. `lib/use-delayed-loading.test.ts` and `lib/use-action.test.tsx` use fake timers (`vi.useFakeTimers()`) for the 200 ms delay and 400 ms minimum. The API client has `lib/api/http.test.ts` (the transport: CSRF, credentials, errors) and `lib/api/index.test.ts` (paths, methods and bodies, plus `@ts-expect-error` checks that wrong queries and paths fail to type-check). `lib/routes.test.ts` covers the workspace route builders and which `?next=` values are accepted; `lib/session.test.tsx` and `lib/use-resource.test.tsx` cover the session hooks, that `useApi()` sends the CSRF token only when signed in, and that the SWR cache is kept per user. `lib/loaders.test.ts` covers the route loaders: the signed-in layout's session and workspaces, 401 → login with `next`, no workspace → onboarding, an unreachable API, signed-in visitors leaving login for an allowed `next`, and `/app` and onboarding redirects. `pages/home.test.tsx` covers the homepage's "Log in" / "Dashboard" button. `pages/auth/forgot-password.test.tsx` renders login and both reset pages in a `MemoryRouter`: the "Forgot password?" link carrying the email in navigation state, the same confirmation for every email, refusals, malformed and dead links (no password asked), retry when the check can't reach the API, password checks, the token sent only in bodies, and arriving at login with the email and a success notice. `lib/use-resource-pages.test.tsx` covers the infinite list: a given page 1, loading more without repeats, stopping at the end, keeping items on failure with retry, and 401 → login.

## Playwright end-to-end (`tests/e2e/workspace.spec.ts`, `tests/e2e/mfa.spec.ts`)

- **Starts its own server:** Playwright's `webServer` runs `make serve-test`, which builds `bin/api` (the Go binary serving the API and the built web app) and starts it on `E2E_PORT` (3100, from `.env.testing`) against a database of its own, `lewcontext_test_<port>`, rebuilt from scratch at every start (`scripts/serve-test.sh`). It never reuses a server already on the port, which may be another run's; `E2E_REUSE=1` asks it to, for iterating against a `make serve-test` you started yourself. `.env.testing` sets `RATE_LIMITS=off`: one run signs up about a dozen users from one IP, past `register:per-ip` (10 an hour) ([../api/rate-limits.md](../api/rate-limits.md#switching-limits-off-for-tests-rate_limits)); quotas still apply. The server's output appears prefixed `[WebServer]`.
- **Settings come from `.env.testing`,** which `playwright.config.ts` loads over the environment, so `npx playwright test` run directly behaves like `make test-e2e` (minus the port check below). The config derives `APP_ORIGIN`, `DATABASE_URL` (the run's database) and the absolute `MAIL_FILE` from `E2E_PORT`.
- **Self-contained:** it signs up unique `e2e-<timestamp>-…@lewcontext.test` users, creates its own data through the UI and the API (22 projects for the pagination flow; 19 workspaces through the API, the 21st refused by the quota, and 4 memberships in the database for the switcher), and afterwards deletes only those users and their workspaces through `psql` on the run's `DATABASE_URL`. It doesn't depend on seeded data. The membership tests (read-only members and viewers; an owner changing a member to viewer, then removing them) add their `member` row through `psql` too, and so does the switcher test: a user can own 20 workspaces, so it fills the rest of the switcher's second page with memberships.
- **Browser:** `/usr/bin/chromium` by default. Without a system Chromium, use the one Playwright installs (`npx playwright install chromium`): `CHROMIUM_PATH=~/.cache/ms-playwright/chromium-<revision>/chrome-linux64/chrome`. Write the whole path: a glob in the variable isn't expanded. If the browser can't launch, every browser test fails within seconds; `test-results/<test>/error-context.md` gives the reason.
- **Covers:** registration → onboarding → the new workspace's dashboard, creating with a pending state, editing on the project page (from its ⋯ menu), "not found" for unknown projects and workspaces, filters, refresh failure with Retry, paging, sorting, server search, back/forward, opening `?page=2` directly, past-the-end, creating from page 2, CSP script hashes and no CSP violations, security headers, mobile layout, session revocation, logout and login, returning to `?next=` after sign-in (with other sites rejected), the prerendered homepage's HTML (title, description, Styletron styles), signed-out `/app` → 302 to login, the old URLs 404ing, creating ("… created.") and switching workspaces, the menus marking Workspace settings and Account & security as the current page, renaming, copying the ID, the owned-workspace quota, infinite scrolling in the switcher, opening the newest workspace after sign-in, "not found" for non-members and members' read-only settings, and hiding the desktop sidebar (the top bar then has the workspace menu, and the account menu only the sidebar): remembered after a reload without it ever rendering docked (a `MutationObserver` added with `addInitScript` watches from the first byte), and the mobile sidebar closing from beside the workspace menu, deleting a project from its row, then the account's only workspace from the last-owner warning (landing in onboarding), then the account from onboarding's menu (login says so, and signing in fails), invitations (an owner invites, the list shows "Sending…" until the worker has emailed each, revokes one; a new account opens its link from the mailbox, signs up through it with the callout and the email filled in, and lands in the workspace with "You joined …"; the link then shows expired; an existing account joins while signed in; the revoked link shows expired; the owner sees both members), and forgot password: requesting a link from login, reading it from the server's mailbox file, setting a new password (the token never in an API URL), signing in with it, and the link refused the second time.
- **Two-factor authentication** (`mfa.spec.ts`): a new account enables it from settings (the QR code hidden until revealed; the test reads the setup key and computes codes with Node's `crypto` HMAC, so no extra dependency), must reveal the recovery codes before the dialog lets go, then signs in with the next step's code (the password alone sets no session cookie) and with a recovery code, disables it with another recovery code, and signs in with the password alone. The e2e server makes a fresh `APP_KEY` at every start.
- **Mail:** the e2e server sends through SMTP to Mailpit (`.env.testing`; `make db` starts it), and the forgot-password and invitation tests read their links through Mailpit's API at `MAILPIT_URL` (`mailedLink`: `GET /api/v1/search?query=to:"…"`, then the newest message). They check the plain-text part carries the same link as the HTML. Runs on other ports share Mailpit, and each finds its own mail by its unique recipients. Watch it live at `http://localhost:8025`.
- Any `pageerror` or CSP violation in the console fails the main flow. API calls made from the test send the page's own Origin and the CSRF token from `/api/auth/me`.
- With `E2E_REUSE=1` against a server with rate limits on, a run fails at the eleventh sign-up (429 "Too many requests"): start that server with `make serve-test`, which turns them off.

## Tips

- The search box has role `searchbox` (it's `type="search"`), not `textbox`.
- Search applies 300 ms after typing stops. After `fill()`, wait for the URL (`toHaveURL(`${projects}?q=…`)`) before the next step. Otherwise a refresh (a `focus` event) runs against the previous query. SWR ignores focus for 5 s after a list mounts, so retry the `focus` event with `expect(…).toPass()` rather than sleeping.
- `page.route(`**/api/workspaces/${ws}/projects`)` matches only the bare path. Use a regex such as `new RegExp(`/api/workspaces/${ws}/projects(\\?.*)?$`)` to catch list requests with query strings.
- Test emails come from a timestamp taken when each Playwright worker starts, and a failed test restarts the worker. Don't share data between tests through module variables; set up what a test needs inside it.

## Running several at once

Other people or agents may run the suite on the same machine. Each run gets its own port and database from one variable, and finds out within a second, before anything is built, if it can't have them:

| `E2E_PORT` | Server | Database |
| --- | --- | --- |
| unset (3100, from `.env.testing`) | `http://localhost:3100` | `lewcontext_test_3100` |
| a port, e.g. `3101` | `http://localhost:3101` | `lewcontext_test_3101`, created on first use |
| `auto` | the first free port from 3101 up | `lewcontext_test_<port>` |

```sh
make test-e2e                  # :3100
make test-e2e E2E_PORT=3101    # a second run beside it
make test-e2e E2E_PORT=auto    # pick a free one; it prints what it took
```

- **The preflight** (`scripts/e2e-preflight.sh`, the first step of `make test-e2e`) checks the test database and Mailpit answer (otherwise: start them with `make db`), then reserves the port: an exclusive lock on `/tmp/lewcontext-e2e-<port>.lock` (`flock`), held for the whole run and released when it ends or crashes, plus a check that nothing listens there. A taken port stops the run with a free port to use instead:

  ```
  Port 3100 is in use: another e2e run (or a server) has it.
  Run this one beside it on a free port:
    make test-e2e E2E_PORT=3104
  Or let it pick one: make test-e2e E2E_PORT=auto
  ```

  A run that gets its port says what it uses: `E2E run: app http://localhost:3104 · database lewcontext_test_3104`.
- **Why a lock, not only a port check:** the build takes a while and the server rebuilds its database before binding the port, so two runs starting together would both pass a port check, and the second would wipe the first's database. The lock is taken before both. It's the same file for every checkout and worktree on the machine.
- **Shared on purpose:** the PostgreSQL container (a database per port) and Mailpit. Go and Vitest runs don't collide: Go tests use throwaway schemas in `lewcontext_test`.
- **`make serve-test` on its own** (a server to check something by hand) reserves the port the same way; under `make test-e2e` it uses the reservation its parent holds. Accounts you make by hand on it vanish at the next start, when its database is rebuilt.
- **Not covered: two runs in the same checkout.** They share `bin/api` and the web build, so one build can replace the other's mid-run. Give each agent its own git worktree.
- **Be considerate of the machine:** several suites at once can overload it and make every run slow and flaky. Check what's running first, and wait for a run to finish if the machine is busy.
